## [Unreleased]

### Added

- The node puts its own GUI helper on a machine. `[gui] helper_upload = ["SOURCE=DIRECTORY"]` (lowest layer only; empty by default) copies the node's executable (`helper_binary` names another) through a files source into the directory, and the helper's command names where it went as `{helper}` (the default command does); the copy is named for its SHA-256, written as a `.part` with mode `0700` and renamed, reused when its bytes are the node's, refused when another file is there (`helper_upload_overwrite`), refused in a directory another account can write to (`helper_upload_shared_dir`) and refused when its header does not match `uname -sm` run through the exec source (`helper_upload_check_platform`). It is no ssh feature: the ssh provider does not know it.
- Providers in other languages. `examples/programs/power_rhai/` is a Bohío power source in Rhai, served by the stock `guatiao-remote-server` with guatiao's Rhai source and started by a node as a provider program; `crates/bohio/tests/program_script.rs` builds the pieces and drives it (and prints `SKIPPED` with the reason when it cannot). `docs/providers.md` gains "A provider in another language", "Which build loads what" (a library in the node's process needs a matching C library and loader; a program or an isolated library needs neither) and says that release archives do not carry `guatiao-remote-server`.
- Libraries in a process of their own. `[providers] isolate` (default `false` in every build, static ones included) and `isolated` (libraries run this way whatever `isolate` says) run a provider library through a host program instead of mapping it into the node: `HOST --stdio --load LIBRARY`, speaking guatiao's remote protocol, so the library needs neither the node's C library nor its loader. `library_host` names the host (default `guatiao-remote-server` beside the node; the node does not look on `PATH`); its file and the library are checked by `check_access`, and the host is started again as a provider program is. `bohio providers` lists an isolated library as the library it is (`loaded` or `failed`, with why); a missing host is that entry `failed` and the node starts. A library that cannot be mapped is `failed` with the hint that `isolate = true` serves it, and the node never switches by itself. A provider a host serves is one instance, so its `[source.<name>]` takes `provider` alone. `docs/providers.md` has the table of which build loads what.
- Providers as programs. `[[providers.program]]` (empty by default, and then nothing starts) names a program the node starts as a child and talks to over its standard input and output in guatiao's remote protocol (`guatiao-source-remote`, no transport feature), so a provider can be any program in any language and built any way: `guatiao-remote-server --stdio --load FILE` hosts a library, and `crates/bohio/examples/program_echo.rs` is a whole provider in Rust. Its providers are registered as a mapped library's are, so `[source.<name>] provider = "<id>"` names them; a provider a program serves is one instance configured where it runs, so that table takes `provider` and nothing else (another key is refused naming it). Keys: `command` (the program's file, then its arguments; not looked up on `PATH`), `name`, `env`, `cwd`, `restart_limit` (`5`; `0` never), `restart_window` (`1m`), `restart_delay` (`1s`), `start_timeout` (`10s`), `stop_grace` (`500ms`), `call_timeout` (`30s`), `max_calls` (`64`) and `max_frame` (`67108864`). A program that exits is `failed` with how it ended, a call in flight fails and the node stays up; the next source lookup starts it again within `restart_limit`, builds its sources anew and a new session works. `[providers] check_access` covers the program file and its directory (`false` runs it and logs `non-default:`; `docs/security.md` has the cost). `bohio providers` lists programs beside libraries (`bohio-providers/1` gains `programs`, `bohio_proto::local::ProgramEntry`); `Sources::libraries` reports them live. New dependency: `guatiao-source-remote` (and, through it, `guatiao-bridge` and `guatiao-libffi`).
- The system's ssh client as an option of the ssh provider. `client = "openssh"` (with `ssh_program` and `ssh_args`) runs each terminal, program and SFTP session as one `ssh` process, so the account's `ssh_config`, Kerberos and `ProxyJump` apply; it cannot resize a terminal, signal a program, pin a host key, take a password or serve an X display or forwarding (the first two are said in `describe`'s `lacks`, the rest are refused when the source is built). The exec and files contract suites and the real-server tests pass against it from Linux and from Windows' `ssh.exe` into a Linux server.
- A GUI helper on another machine. `bohio gui-helper --stdio` serves the node over its standard input and output, and `[gui] source = ["NAME"]` (an exec source; `"NAME=COMMAND"` for another command line; lowest layer only; `source_retry`, `10s`) makes the node start it through that source (an ssh source's login) and serve that machine's desktop as a session `exec:NAME`: a Windows, macOS or Wayland desktop over SSH with nothing but `bohio` on it. `bohio::gui::helper_exec::ExecHelper` and `Node::serve_exec_helpers` for an embedding application.
- The desktop of a machine reached over SSH. An ssh source serves the machine's X display as a desktop (`x11_display`; the screen is captured and clicked through a channel to the display's socket, the cookie read with `xauth list`), and with `x11_forward` (and `x11_trusted`, which it needs) the programs it starts open their windows on the node's own display, as `ssh -X` does: the node checks the cookie it gave the machine, replaces it with the display's own and relays each connection (`x11_max_connections`). `x11_socket_dir`, `xauth` and `x11_local_display` are settings. The X11 backend and the `Desktop` types moved to a new crate, `bohio-x11` (`bohio::gui` re-exports them; the backend now connects by display name or over a stream a `Connector` hands it, and logind's lock hint is its `logind` feature); a Windows node serves a Linux machine's desktop this way.
- An ssh provider. `[source.<name>] provider = "ssh"` serves another machine's terminal and processes through SSH with nothing of Bohio installed on it (`providers/ssh/`, feature `ssh`, in `default`; `providers/ssh/plugin/` is the same provider as a library). Login uses an ssh agent's keys (the OpenSSH agent's pipe or Pageant on Windows, `SSH_AUTH_SOCK` elsewhere), key files and a password given as a secret reference; the host key is `strict` by default (a `sha256:` pin or `known_hosts`), `tofu` and `off` are the operator's weakening, logged as `non-default:` and costed in `docs/security.md`. `max_channels` (`8`, below sshd's 10), the timeouts, the keepalive and the reconnect are settings. A source that cannot connect is `unavailable` with the reason and the node starts regardless. `bohio remote HOST exec --source NAME` and the agent tools' `source` run a program on the machine; `shell --source NAME` opens its login shell. Pure Rust over ring: `cargo tree -i aws-lc-sys` finds nothing.
- Files on a machine reached over SSH. The `ssh` provider (`providers/ssh/`, feature `ssh`, in `default`) serves a `bohio_files` source over SFTP with its terminal and exec sources: POSIX names whatever the node runs on, the extensions the server advertises offered and the rest in `lacks`, no `confined` (said in `describe` and `docs/security.md`), `sftp_in_flight` and `sftp_packet` for latency-bound links. A request names the files source with `source` (`bohio-read/1`, `bohio-write/1`, `bohio-hash/1`, `bohio-walk/1`, `bohio-search/1` and the control request), refused as `denied` when the grant does not reach it; `--source NAME` on `remote read`, `write`, `hash`, `put`, `get`, `walk`, `glob`, `search` and `sync`, `bohio_client::Sourced` for a library, and a `source` argument on the agent's file tools. `fs::locate` takes the source's syntax.
- Processes are a capability of the node's sources. `bohio_api` gains the `bohio_exec` kind (`ExecSource`, `Process`, `ExecStart`) and its contract suite `contract::exec`; `native` is the first exec source and `exec::serve` starts every process through one, so a second provider (a machine reached over SSH) serves the same requests with the same grants. `[access] exec` lists exec sources (`"native"` and `"none"` keep their meaning), `info.access.exec` lists them as it lists terminals (and `fs` lists the file sources), and `bohio-exec/1`'s request takes an optional `source`. The engine keeps every grant check and the tree rules: the process ends with its last holder, descendants holding an output open are ended after `[execution] drain_timeout`, and a source reconfigured while a process runs ends it.
- Files are a capability: the `bohio_files` kind (`FilesSource`, `Directory`, `DirReader` and `File` of `bohio-api`, with `bohio_api::contract::files`) and `native` as its first provider. Every filesystem engine (control calls, read, write, bundle, hash, walk, search, follow, move, copy, media images) reaches files only through it, through `fs/vfs.rs`. `[access] fs` lists file sources (`"native"` and `"none"` keep their meaning) and `info.access.fs` lists them like the other capabilities. `[source.native] list_chunk` (`256`) is the entries one read of a listing returns.
- Provider libraries loaded at run time. `[providers] paths` (files, or directories of `.so`, `.dll` or `.dylib`; empty by default, and then nothing is read or mapped) names libraries the node maps at start, through guatiao's `load_file`, so `[source.<name>] provider = "<id>"` can name what they offer. Each candidate is read as data first and only a library that declares a Bohío kind is mapped; a file that is not a library, declares no Bohío kind, is already loaded (a stale copy beside a newer one) or offers a provider id a built-in holds is reported `skipped` with why, a library that cannot load is `failed`, and one failure never stops the others. The start log and `bohio providers` (on the node's local endpoint, `bohio-providers/1`; `--json`) list each library with its SHA-256. A library, or the directory holding it, that another account owns or may write is refused unless `[providers] check_access = false` (only the lowest layer sets it), which loads it and logs `non-default:`; loading is unpinned (there is no `pins` key until guatiao can check bytes before it maps them), so `docs/security.md` says what it costs. The statically linked musl builds (the Linux release archives) map libraries too, on x86_64 and aarch64: guatiao starts the system's own `ld.so` and glibc inside the node, so the machine needs glibc and its dynamic linker at the usual path (`[providers] ld_so` names another), and a library is built for glibc. One foreign C library serves the whole process, it takes signal 33 when it starts (the start is refused when the node already handles signal 32 or 33), and library code runs on threads that library made. `[providers] dlopen` (`auto`, `system`, `foreign`), `ld_so` and `allow_reserved_signal_handlers` (the last two from the lowest layer only) are guatiao's loader settings with its defaults; a weakened one is logged as `non-default:`. Tests of a static build take the libraries built for glibc from `BOHIO_LIBRARY_DIR`. `providers/terminal/serial/plugin/` is the `serial` provider as a library in one `providers!` line. `Sources::load_libraries` and `Sources::libraries`; `Node::new` loads before it builds the sources. Feature `serial` is on in `default` and no longer implied by `cli`, so a build without it can load the provider as a library. The path-ownership check moved from `cli/access.rs` to `bohio::ownership` (crate-private) and covers a library file and its directory.
- A service account's own desktop on Linux. `[source.native] own_session = "x11"` makes a node that runs as a service account serve the headless desktop that account's own user units run: the runtime directory (`/run/user/UID`) and the display (`:UID`) come from the node's uid, the directory must be the account's own and mode 0700 (else `info` says why and names the path), there is no lock screen (`locked` is `false`, `lock_detection` is `false`), and input is XTest on the X server. `own_session = "wayland"` serves the compositor through the portals (a view on a wlroots compositor) and `own_runtime_dir` names another runtime directory. `packaging/systemd/own-desktop/` is the complete example: the system unit (`User=` the account, after its `user.service`), the user target and units (headless sway, a rootful Xwayland, and with `--portal` the distribution's PipeWire, WirePlumber and portal units), the compositor's configuration, and `install.sh`, which creates the account, enables lingering, installs and starts the units, is idempotent, prints each step, and takes `--dry-run` and `--uninstall`. `tools/own_desktop_units.sh` proves the user units as shipped in the running account's own user manager.
- Agent tools for the desktop. `bohio mcp --gui` lists `screenshot`, `click`, `move_pointer`, `drag`, `scroll`, `type`, `key`, `wait`, `displays`, `cursor_position`, `clipboard_read`, `clipboard_write` and `gui_watch` (without `--gui` none is listed or callable), the same calls as a local computer-use loop, bounded by the host's `gui.view`, `gui.input` and `gui.clipboard`. A screenshot waits on the host for the screen to settle and is fitted there to `max_width` x `max_height` (1280 x 800), PNG unless larger than `--gui-max-image-bytes` (1048576), then JPEG 80; `click`, `drag`, `scroll` and `move_pointer` take points in the last screenshot of a display and the server maps them back by its region and scale (`space: "display"` for raw pixels), refusing a point outside it with the bounds; `--gui-after-action screenshot` answers every input with a settled screenshot. `bohio_client::tools::Tools` gains the same calls as methods (`screenshot`, `click`, `move_to`, `drag`, `scroll`, `type_text`, `key`, `wait_settled`, `cursor`, `gui_displays`, `clipboard_read`, `clipboard_write`) over one `bohio-gui/1` stream kept per host, and `Settings` the `gui_*` bounds. The pointer move is `move_pointer` because `move` is the file tool. `docs/agents.md` carries the warning that what a screen shows is untrusted input. The `gui_host` example serves the painted test desktop (`--scene painted`) and prints each input event it takes.
- The per-user GUI helper: a node that runs as a service (a Windows service in session 0, a systemd unit) has no desktop, and `bohio gui-helper`, started at a user's logon, lends that user's desktop to it. The helper connects out to the node's helper endpoint, says which session it serves (`bohio-gui-helper/1`) and serves the node's `bohio-gui/1` streams over the user's own desktop, so `gui info` lists the session (`ACCOUNT:NAME`) and a peer's snapshot, input and clipboard go through it; the node checks the peer's grant, its limits and each input frame as for its own desktop and ends a relayed stream at `[link] recheck` when the grant loses what it opened with, and a helper that ends ends them `unavailable`. Both ends check the other's account from the operating system's answer about the connection: the node serves only `[gui] helper_accounts` (a connection of any other account is closed unread; on Unix the socket's directory must be one only the node's account owns and writes), and the helper exits 1, naming both accounts, before it sends anything when the endpoint is served by an account other than `--node-account` / `[gui] node_account` (default `NT AUTHORITY\LocalService`, `bohio` on Unix). The helper holds no key and reads no `[peer.*]`; its user's own `[gui]` only narrows what the node allows. New `[gui]` keys: `helper_accounts`, `helper_endpoint`, `node_account` (the lowest layer alone sets them) and `max_helpers` (`8`); `Context` of `bohio::gui::serve` gains `session`; `bohio::gui::helper` (`HelperListener`, `Node::serve_helpers`, `run`, `resolve_account`) for an embedding application. `packaging/systemd/bohio-gui-helper.service` (a user unit), `packaging/launchd/bohio-gui-helper.plist` and `packaging/windows/bohio-gui-helper.xml` (a Task Scheduler task at logon) are files only, and `bohio.service` gains `RuntimeDirectory=bohio` for the socket.
- The container image builds from the `deps` branch. `python tools/build.py container build` and `container test` copy the pinned deps commit in, install the toolchain the SDK lock names with a hash-checked `rustup-init`, and run `cargo build` and `cargo test` with no network; `docker` takes the same command. `.env`, `.env.local` and `--env KEY=VALUE` override sources and locations (rustup and package mirrors, base images that stay pinned by digest, a local deps checkout, proxies, an extra CA certificate, the engine) without changing a hash or version; `.env.example` lists every key, and `--print` shows the settings and the engine command without running it. `sdk check` holds the Containerfile's pins to `tools/sdk.lock`.
- Native build keys in `.env` and `.env.local`: `VSINSTALLDIR`, `VCTOOLSINSTALLDIR`, `WINDOWSSDKDIR`, `WINDOWSSDKVERSION`, `LIBCLANG_PATH`, `LLVM_DIR` and `SDK_HOME` point `python tools/build.py sdk install` and `release build` at the Visual Studio, Windows SDK and LLVM of a machine, each path checked when it is read; `MSVC_SPLAT_DIR` is listed for the release overlay's optional cross stage. See `docs/building.md`.
- Profiles: named defaults for the transfer settings. `[profile] name` (`default`, `lan`, `weak-host`, `slow-link`, `fat-link`) lays a table of defaults under the configuration files, so a key any file sets wins, key by key, and a profile sets no key that cannot be overridden and no `[peer.*]` table; the highest layer that sets the name decides, an unknown name is refused naming `profile.name`, and an error in a value only the profile supplied names `profile NAME`. `fat-link` raises `[link] bulk_window` to 8 MiB for a long path with room in it (a round trip of a few hundred milliseconds), where the default 1 MiB window limits one stream. `bohio::profile::table` and `NodeConfig::with_profile` give an embedding application the same table. `bohio_client::profile::Profile::defaults` says what a client asks for (compression, delta, comparison, streams, the bulk window, when to prepare); `bohio remote --profile NAME` and `[client] profile` choose it, `--delta` and `--compare` of `put`, `get` and `sync` default to it, and a flag or a key the file sets wins. `bohio config check` prints every transfer setting with whether its value comes from a file, a profile or the default (`--json`: `profile` and `transfer`), and `bohio-bench` takes `--profile`. `docs/profiles.md` and `examples/profiles/` have the tables, what each costs and where each was measured.

- Latency: many calls on the way at once, and one file on several streams. `bohio_client::control::Control` gains `submit` and `collect` (a call sent now, its answer read later; answers that arrive for other calls are kept for them), `abandon`, and `call_many`, which sends a batch on one thread while reading the answers on another, in order and each its own result, so a batch larger than the stream's window cannot deadlock and a call that times out leaves the stream and the rest intact. `Fs::stat_many` and `Fs::list_many` use it, and `Connection::fs()` keeps one control stream warm for a command that makes many short calls. The host already answered in order, so nothing changed on the wire; `docs/protocol.md` has a "Pipelining" note. `bohio_client::parallel` has `get_parallel`, `put_parallel` and `read_parallel`: a file of the host read (or written) in ranges on `streams` streams, spread over one link or several (each its own proof and congestion window), each range its own stream with its own receive window. A get writes each range at its offset into a temporary sibling and renames it after the whole file's SHA-256 matches the host's; a put creates `.NAME.bohio-part-HEX` beside the target, writes ranges with `at` streams, checks the digest and moves it over the target, and a failure removes it. `bohio remote ... get|put|read` take `--parallel N`, `--links M` and `--range BYTES`, defaulting to the new `[client] parallel_streams` (`1`), `parallel_links` (`1`) and `parallel_range` (`0`). `bohio-bench` (feature `pipeline`) has `open_call_xN`, `stat_xN_pipelined`, `read_<size>_parallelN` and `remote_via_read_<size>`. No default of the link or the transfer changed.
- Sources and providers: how a node reaches the system it is for. A **source** is a configured instance of a **provider**, and each capability (terminal, desktop, power, virtual media) is a guatiao kind of the new `bohio-api` crate (`TerminalSource`, `DesktopSource`, `PowerSource`, `MediaSource`, their object kinds, the models, a contract suite `bohio_api::contract` every provider passes, `bohio-api.kinds.json` for a provider written in another language and in-memory sources behind feature `testing`). `[source.<name>] provider = "<id>"` plus that provider's own keys (checked against its schema before it is built: `source.<name>.<key>` names a bad one) and `[access]` (`terminal`, `desktop`, `power`, `media` lists whose first is the default; `fs` and `exec` `native` or `none`) choose them; a node with neither is what it was. `native`, this node's own pseudo-terminal and screen, is a provider like any other, so `shell::serve` and the GUI engine ask `bohio::access::Sources` and nothing is reachable only because it is built in. `[gui] backend` and the `[gui] windows_*` keys moved to `[source.native]` (`windows_capture`, `windows_frame_wait`, `windows_capture_idle`, `windows_clipboard_wait`, plus `read_chunk`, `queue_chunks`, `clipboard_max_bytes`). `Node::with_sources`, `Node::sources`, `Sources::reconfigure` (a changed table builds a new instance and what runs on the old one ends `unavailable`).
- The console of a source that starts no program. `bohio-provider-serial` (feature `serial`, on with `cli`) is the `serial` provider: `path`, `baud_rate`, `data_bits`, `parity`, `stop_bits`, `flow_control`, `dtr`, `rts`, `reopen_after` (`1s`; the port is opened again after it vanishes) and `queue_bytes` (`65536`). `bohio-shell/1` takes `program` of type `console`, and `bohio remote HOST console [--source NAME] [--from OFFSET]` attaches to the node's console of that source (one session the node owns, `console:<source>`; kept output, a newer attach supersedes, a `kill` only detaches; leave with `Ctrl-]` then `q`); the agent session tools read it with no new tool. `started.pid` is optional and `bohio-gui/1` takes a `source`. `examples/console_node.cfg` is an agentless node.
- `info.access`: each source a peer reaches, with its provider, whether it is the default and available (and why not) and what it offers and lacks, asked of the providers at every `info`. `bohio remote HOST info` prints a row per source, and an agent's tools for files or processes are unavailable (and `bohio mcp` does not list them) on a node whose `[access] fs` or `exec` is `none`.
- Grants per source and secret references. `[peer."<id>"] sources = [..]` names the sources beyond each capability's default a peer may use (without it, the defaults alone; a source added later grants nobody anything), checked when a stream opens and at every `[link] recheck`. Permissions `power` and `media`. A setting a provider marks sensitive holds a reference (`file:PATH`, `credential:NAME`, `keyring:SERVICE/ACCOUNT`), never the secret: a literal is refused naming the key without quoting it; `Node::with_secrets(resolver)` says how references are read (`bohio` reads `file:` from a file only its owner may read and `credential:` from `$CREDENTIALS_DIRECTORY`; this build has no keyring); `[secrets] max_bytes` (`65536`).
- `bohio-power/1` and `bohio-media/1`: one request and one answer each. `[power]` and `[media]` (`enabled` `false`, `action_timeout` `60s`, `max_streams` `4`), `bohio remote HOST power status|on|off|soft-off|cycle|reset|nmi [--source]` and `media status|insert URL|insert --path P|eject [--slot]` (an image of the node must lie under the peer's `fs_roots`, and the source reads it through the host), `NodeEvent::Power` and `NodeEvent::Media` (they never name an image), agent tools `power_status` and `media_status` (actions stay off the tool surface). No provider for either ships yet: this is the framework, tested with in-memory sources. `docs/providers.md` shows how to write a provider; `provider_echo` is its example.
- The Linux Wayland desktop backend (feature `gui-wayland`, off by default): a node started in a Wayland session serves it through `xdg-desktop-portal` with a RemoteDesktop session and ScreenCast monitor sources, or ScreenCast alone where the portal has no RemoteDesktop (`xdg-desktop-portal-wlr`), which is a view (`info` says `input: false` and input is `unsupported`). Each monitor is a display read from its PipeWire stream, input is `notify_pointer_motion_absolute`, `notify_pointer_button`, `notify_pointer_axis_discrete` and `notify_keyboard_keysym`, and there is no clipboard. The portal's dialog is the system's approval and shows at the first request that reaches the node, `info` included. `[source.native]` keys, each with its default in `examples/bohio.cfg`: `wayland_persist` (`none`, `node`, `always`), `wayland_restore_file` (the command fills it from the data directory), `wayland_capture_wait`, `wayland_start_wait`, `wayland_retry` and `wayland_max_repeat`. `bohio::gui::{WaylandDesktop, WaylandSettings, Persist}`. The feature links the system libpipewire-0.3, so it is for glibc builds and stays out of the static release archives; a build without it reports a Wayland session as unavailable and names `gui-wayland`. `tools/wayland_headless.sh` runs a command inside a headless sway with PipeWire, WirePlumber and the portals on a private D-Bus session, for `tests/gui_wayland.rs`. New dependencies (feature `gui-wayland`, Linux): `ashpd`, `pipewire` and `pollster`.
- The Windows desktop backend: a node that runs in the user's own session (a logon task, a terminal, not the service) serves that session's screen, keyboard, mouse and clipboard text over `bohio-gui/1`, and `bohio serve` uses it when `[gui] enabled` and `backend` is `auto` or `windows`. Capture is DXGI Desktop Duplication with GDI where duplication cannot serve (a rotated display, an HDR one, a remote session), every display, in physical pixels (the process becomes per-monitor DPI aware, v2, when the backend starts); the pointer is reported apart and never drawn into the pixels. Input is `SendInput` on the virtual screen, so a display left of or above the main one is reachable; keys are virtual keys (a letter or digit by its key, any other character typed as itself), `text` is typed as UTF-16 whatever the layout with a line break as Enter, a wheel notch is 120. A point outside its display refuses the whole batch. While the secure desktop has the screen (the lock screen, a sign-in or an elevation prompt) capture and input are `unavailable` and say so, and a node in session 0 reports `available: false` with the way out. New `[gui]` keys, each with its default in `examples/bohio.cfg`: `windows_capture` (`auto`, `dxgi` or `gdi`), `windows_frame_wait` (`250ms`), `windows_capture_idle` (`10s`) and `windows_clipboard_wait` (`500ms`). `bohio::gui::{WindowsDesktop, WindowsSettings}` for an embedding application. `platform/gui/windows.rs` and `windows_capture.rs` join the files `tests/unsafe_files.rs` lists; the `windows` crate (already in the lock through `win32job`) is a direct dependency.
- The Linux X11 desktop backend: a node started in an X session (`DISPLAY`) serves that display over `bohio-gui/1` with `x11rb`'s pure-Rust connection (no libxcb, so the static musl archive keeps it) and no `unsafe`. Each RandR 1.5 monitor is a display (the root window when the server has none), a capture is `GetImage` of the root converted from the visual's masks (and, where the root cannot be read, the viewable windows over black), input is XTest on the root (a point on a second monitor is its offset plus its own), keys and `text` go through the keyboard mapping and a character with no key is typed through a spare keycode bound to it for `x11_key_wait`, and the clipboard is a selection the node owns. The lock state is logind's `LockedHint` over `zbus`; with no logind it is unknown and `info` says `lock_detection: false`. - What a host runs on, where its programs are, and a read that follows a file. - SOCKS5 and jump hosts, the two client compositions of the forwards. `bohio remote ... forward -D [BIND:]PORT` serves SOCKS5 here (RFC 1928, no authentication, CONNECT with IPv4, IPv6 or a domain name that the host resolves): each client's CONNECT is a `bohio-connect/1` to its target under the peer's `forward.connect` rules, answered after the host connected (`0x00`; `0x02` not allowed, `0x04` unreachable or a name that does not resolve, `0x05` refused, `0x06` timeout; BIND and UDP ASSOCIATE `0x07`; another address type `0x08`); `[forward] socks_timeout` (`10s`, not zero; `--socks-timeout`) bounds a client's handshake, and `max_local_connections` its connections. `--jump ENDPOINT` (repeatable) with `--jump-server ID` reaches a host through others as `ssh -J` does: the first is dialed, each next hop (`tcp://`, `pipe://`, or `stdio://PROGRAM` run on the previous host with its standard input open) is a stream the previous one carries, and every hop proves its own host end to end, so a jump holds only `forward.connect` for the next address (or `exec` of one program) and cannot stand in for the host behind it; an error names the hop. No message changes.
- Trees, bundles, host-side moves and streaming writes. `bohio-walk/1` (needs `fs.read`) lists whole trees on one stream: roots as frames, `depth` (`0` is a batched `stat`), `follow` (inside the root, each directory once by device and inode), `include` and `exclude` globs, digests of each file, entries batched depth first with each directory's names sorted, unreadable directories and links that leave the root as item errors, each root decided by the grant as it is then, the entries compressible as every other stream is; `[walk] max_streams` (`4`) and `max_entries` (`1000000`). `bohio-read/1` and `bohio-write/1` take `items: true` for a bundle: many files on one stream, each with its own header, data and `done` or item error, one compression context across them, each put in place on its own (a write item may carry `modified`, set before the rename so a sync's next quick check by size and time matches; `[filesystem] max_bundle_items`). The control gains `move` (a rename, else on another filesystem a copy that keeps mode and time and then the removal, on the host), `truncate`, and `copy` with `recursive` and `preserve` (links stay links; `[filesystem] max_tree_entries`); metadata gains `device`, `inode` and `links` on Unix. A rename or move without `overwrite` is now decided by the operating system in the rename itself on Linux (`renameat2` with `RENAME_NOREPLACE`), macOS (`RENAME_EXCL`) and Windows (`MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`), for files and directories, so a target made in between is not replaced; FreeBSD and a filesystem that refuses the flag use a hard link and an unlink for a regular file and keep a check-then-rename for a directory. A new file, `platform/rename.rs`, holds the Windows call (listed in `tests/unsafe_files.rs`). The host removes the expired kept writes of every granted root when it starts (`Grants::roots`). `append` and `at` writes take `flush` (the host syncs when `[filesystem] sync_writes` and answers the bytes written), and a `replace` may ask to `resume`: the host keeps the temporary file for `[filesystem] resume_ttl` (default `0s`: none) and a later write in mode `resume` for the same path, from the same peer, goes on at the offset the host holds, its digests covering the whole file. `info.transfer` reports `walk`, `walk_limits`, `bundles` and `resume`. `bohio_client::{walk::walk, bundle::{get_many, read_bundle, put_many}, range::RangeReader (Read + Seek over bounded ranges with prefetch), sync::sync_tree (walk both sides, compare by size and time, a digest or blocks, move small files in bundles and large ones by delta, `delete`, `dry_run`, `parallel`), Fs::{move_to, truncate, copy_with, spawn_control}, Writer::{flush_remote, token, resumed_at}}`; `bohio remote ... walk PATH [--depth N] [--follow] [--include GLOB] [--exclude GLOB] [--hash ALG] [--compress ALG] [--format text|json]` and `sync push|pull LOCAL REMOTE [--delete] [--dry-run] [--compare meta|hash|blocks] [--bundle-max BYTES] [--bundle-items N] [--parallel N] [--compress ALG]`. `docs/protocol.md` has the CDDL, `vectors/walk.json` (new) and the others the frames, and the benchmark harness (`local --wan DELAY_MS[:MBIT]` puts an in-process delay and rate between it and the host) has the `walk_`, `bundle_`, `file_` and `sync_tree_` scenarios behind its `walk` feature.
- Programs that survive a lost link, and a way to pick them up again: detached sessions. A new permission, `session`, and a `session` in the request of an `exec` or a `shell` (`name`, `scrollback`, `on_full`, `linger_ms`) make the host start the program as it always does but keep it running when the stream ends (a dropped link, a killed client, a closed command), with its output kept in memory under one byte offset across standard output and standard error. `started` carries the session's id; `bohio-attach/1` (a new protocol, needing `session`) takes `{session, from}` and answers `attached {kind, from, lost}` and then the exec's or the shell's own frames from that offset and live, and the client's input, resizes, signals and `kill` go to the program as before. One stream is attached at a time (a newer attach closes the older with `superseded`). `on_full` is `pause` for an exec (the program waits for a reader instead of losing output) and `drop_oldest` for a shell (the oldest output is forgotten and `lost` counts it). The control calls `sessions` (the caller's own, with `next` and `buffered`; an `admin` sees every peer's) and `end_session` (a signal, `kill` by default; another peer's id is `not_found`) manage them. A session ends at its program's exit (kept `keep_exited`, `1h`, for a reattach to read), at `end_session`, at its `linger` (`24h`) while nobody is attached, when its owner's key stops being accepted or its grant stops holding `session` and `exec` or `shell` (looked at every `check_every`, `5s`), and with the host. `[sessions]`: `enabled`, `max_detached` (`16`), `max_per_peer` (`8`), `scrollback` (`1048576`), `max_scrollback` (`16777216`; a request for more is `bad_request`), `linger`, `keep_exited`, `check_every` and `queue_frames` (`16`); a session holds its `max_processes` or `max_sessions` slot; `info.sessions` reports what the host keeps. A session's streams are not compressed. `bohio remote ... exec --detach [--name N] [--scrollback B] [--on-full pause|drop-oldest] [--linger SPAN]` and `shell --detach` print the id and exit, `attach ID [--from OFFSET]` picks a session up (typing, Ctrl-C and the exit status as for `exec` and `shell`), `sessions [--format json]` lists and `end ID [--signal NAME]` ends. `bohio_client::{session::attach, exec::Exec::attach, shell::Shell::attach, control::Control::{sessions, end_session}}`; `NodeEvent::Session` tells each start, attach, detach and end by id. The rule that a tree always ends with its stream has this one exception, in `AGENTS.md`. `docs/protocol.md` has the CDDL and `vectors/attach.json` the messages.
- Signals to a running program, and a program on a terminal with a deadline. A `signal` frame (`0x15`, `exec` and `shell`) delivers `interrupt`, `terminate`, `hangup`, `quit`, `user1`, `user2` or `kill`, and the host answers each with `signalled` (`0x08`: `delivered`, and a `message` when it was not or when delivering meant something else; not an error). On Unix the signal goes to the program's process group (`kill` ends the whole tree); on Windows `terminate` and `kill` end the tree through the job object, `interrupt` is a `CTRL_BREAK_EVENT` to the program's group when the host has a console (the program then starts in a group of its own on that console) and `delivered: false` when it has none, as a service does, and the other signals are `delivered: false`. On a terminal (a shell, `exec --pty`) a Windows `interrupt` types Ctrl-C at the pseudo-console, which reaches the program unless Ctrl-C is ignored in the host's process chain (inherited; reproduced on the development machine: the same test reaches its program from PowerShell and not from Git Bash). `info.exec.signals` and `info.shell.signals` list what a host delivers. `bohio-shell/1` takes `timeout_ms` and its exit says `timed_out`, so `bohio remote ... exec --pty` is `exec` on a terminal (output and error as one stream, the terminal's size and typing), under the `shell` grant. Ctrl-C of `bohio remote exec`, `shell` and `attach` is an `interrupt` to the program instead of the end of the command (on a terminal, the typed byte reaches the program's terminal), and a second within `--kill-after` (`2s`) is a `kill`; a signal the host did not deliver is told on standard error. `bohio_client::{exec::Exec::signal, shell::Shell::signal}` and `Event::Signalled`; `ctrlc` is a new dependency of the command. An exec waiting for a client that reads slowly no longer reports its exit before its output.
- Forwards that survive a lost link, as a WireGuard peer does: nothing is run again when the other side comes back. `[peer."<id>".forward]` gains `local = ["127.0.0.1:5432=db.lan:5432", "unix:/run/app.sock=pipe:app"]` and `remote = ["127.0.0.1:0=127.0.0.1:8080"]`, the `-L` and `-R` grammar of `bohio remote ... forward` (a bad entry is named by `bohio config check`; they are what this node does toward the peer, beside the grant's `connect` and `listen`, which are what the peer may do here, and `bohio peer approve` keeps them). The node owns them: a `local` listener is bound once and stays up while the link is down, a connection that arrives then waits up to `[forward] wait_for_link` (`30s`; `0` closes it at once) for the link and is closed after, and each `remote` entry is asked of the host again whenever a link to the peer comes up, for the port the host chose the first time (so the peer's `listen` rule must cover that port, for example `127.0.0.1:*`, and AI6's `reopen_forward` finds its port again). The entries are read again every `[link] recheck`: an entry added is started, an entry removed stops and its port closes. `bohio serve` prints `local ADDRESS -> TARGET peer ID` and `remote ADDRESS -> LOCAL peer ID` each time one listens, `local|remote down ...` and `local|remote failed ...`; `NodeEvent::Kept` tells the same, `Node::run_forwards` runs them for an embedding application (`forward::Declarations`, implemented by `LayeredPeers`), and `forward::{LocalSpec, RemoteSpec}` parse an entry. `bohio remote ... forward`, `connect` and `listen` make the link again by default after one that was up is lost, with the waits of the peer's `[dial]` table (`retry_min`, `retry_max`, `retry_factor`, `retry_jitter`, found by `--server`, `--via` or the endpoint, else the dial defaults) or `--retry-min`, `--retry-max`, `--retry-factor` and `--retry-jitter`; `-L` listeners stay bound meanwhile, `-R` and `listen` ask the host again for the same port, `connect` waits for a link that ended before it was answered, and `--once` keeps the old exit with status 1 on loss. The first link is made once either way, and a bridged connection that is running still ends with its link. Over `--via` only the link to the node is kept: a connection that arrives while the node has no link to the peer is refused, which a declared forward in the node's own `bohio.cfg` waits out instead. `bohio_client::keep` has `Backoff`, `Jitter`, `Links`, `Relink` and `Reconnecting`; `DialConfig::backoff` gives a table's waits.
- A client waits instead of failing when the host is full for the moment. An open the host refuses because it is over a limit (`[link] max_pending_opens`, `max_streams`, `max_per_protocol` or `max_opens_per_minute`, which the host closes with the text `over a limit`) an open the link could not queue behind the others of a burst (`NoProgress`), and a `connect` or `accept` it answers `busy` (`[forward] max_connections`, `max_connections_per_peer`) are tried again every `[forward] open_retry_interval` (`100ms`, each moved by up to a quarter of itself) for `[forward] open_retry` (`10s`; `0` never retries) before the connection fails, so a burst of 64 connections through one `-L` is served as the host drains instead of losing most of them to a pending-open bound of 8 and a per-peer bound of 16. Those bounds keep their defaults: the retry is the client's, so a host's bound still caps what a peer costs it. A refusal for a grant, a revoke or any other answer is still final at once. `ForwardSettings` gains `open_retry`, `open_retry_interval` and `wait_for_link`; `Open` gains `open_cause` (with `connect::Cause`) and `relink_wait`. No message changes.
- Deltas: move only what changed (rsync's algorithm, streamed, specified in `docs/protocol.md` "Deltas" so another language can implement it). `bohio-hash/1` takes
  `blocks` and sends each item's block signature (a rolling weak checksum and a strong hash of each block, in `hash-blocks` frames); `bohio-read/1` takes `delta`
  (the client sends the signature of its old copy and the host answers `copy` and data frames), and `bohio-write/1` has the mode `delta` (the client sends `copy`
  and data frames against the target the host holds), applied atomically as `replace` is and refused with the new error `changed` when the target is not as the
  client saw it. A delta write reads the target, so it needs `fs.read` as well as `fs.write`. Compression composes: literal bytes are compressed as the stream says.
  The block size is about the square root of the file's size as a power of two, between `[delta] min_block` and `max_block`; `[delta]` also has `max_signature_bytes`,
  `min_size` and `max_expansion`, and `info.transfer.delta` says what a host offers. `bohio_transfer::{rolling, signature, delta, apply}` (no I/O; the signature, a
  window of one block and one frame of literals are the memory, never the file), `bohio_client::sync::{compare_file, put, get}` (a quick compare by size and time,
  then a digest, then blocks; `auto`, `always` or `never` for a delta; `Moved` says the wire bytes), `bohio_client::hash::hash_blocks`, `Writer::copy`,
  `Control::transfer` (what the host offers, from its `hello` reply, with no `info` permission), `bohio remote ... put` and `get` (`--delta`, `--compare`,
  `--compress`, `--block-size`; one line `sent W of S (copied C, literal L)`), and `vectors/delta.json` (weak sums, a signature and steps).
- A Windows program of `exec` starts inside its job object (`PROC_THREAD_ATTRIBUTE_JOB_LIST`), so a child it starts in its first instructions is in the tree and ended with it. A shell session's terminal still starts its child itself and joins the job just after.
- A killed host ends the programs it started (Unix). Each `exec` program and each shell session gets a guardian process that signals the program's process group (and a shell's session, on Linux) when the host's end of a pipe closes, so a `SIGKILL`ed `serve` no longer leaves its trees running on Linux, FreeBSD and macOS. `[execution] host_death` and `[shell] host_death` choose `kill` (the default), `term` or `leave`.
- WebTransport's UDP payload sizes and path-MTU discovery are settings: `[[listen]] mtu_initial`, `mtu_min`, `mtu_discovery` and `mtu_upper_bound` for a `webtransport` entry, the same four keys in `[peer."<id>".dial]`, `--mtu-initial`, `--mtu-min`, `--mtu-discovery` and `--mtu-upper-bound` on `bohio remote` and `bohio join`, and `Endpoint::with_mtu` in `bohio-client`. The defaults are QUIC's (`1200`, `1200`, on, `1452`), so nothing changes unless set. A path with a smaller MTU than 1452, such as a site tunnel, loses every probe above it, which the OS may report as a send error (Windows 10040, a 1389-byte datagram): set `mtu_upper_bound` to the path's size or `mtu_discovery = false`. A size below 1200 is refused naming the value.
- A host's desktop over `bohio-gui/1`, and the person at the screen told. Three new permissions, all off by default: `gui.view` (snapshots and the wait for the screen to settle), `gui.input` (keyboard, mouse and scroll, with the desktop user's whole authority) and `gui.clipboard` (text, beside one of the others); `[gui] enabled = false` also gates the host. One stream is one view: `ready`, then `snapshot` (PNG, JPEG or lossless WebP, a display or a region, scaled to fit `max_width` and `max_height`, with the pointer and an optional settle), `input` (move, button, scroll, key, text and wait, in order), `settle` (one round trip until the screen is quiet), the clipboard's text and `state` whenever the desktop changes. `[gui]` holds `max_streams` (`4`), `max_streams_per_peer` (`2`), `snapshots_per_minute` (`120`), `max_snapshot_pixels`, `formats`, `jpeg_quality` (`80`), `max_input_rate` (`1000`), `max_batch_events` (`256`), `max_text` (`4096`), `max_batch_wait` (`5s`), `input_when_locked` (`false`), the settle times, `clipboard_max_bytes`, `indicator` (`notify`), `indicator_linger` (`30s`), `approval` (`none`), `approval_timeout` (`60s`) and `approval_ttl` (`15m`). A new error code, `unavailable`, says a desktop exists but cannot be used now (locked, not at the screen); `info.gui` reports the backend, the displays and the state, and the sessions only to a peer with a GUI permission. `Node::with_desktop` takes any `gui::Desktop` (a backend, or an application's own); `NodeEvent::Gui` tells each start, end, clipboard use and refusal as counts, never pixels or typed text. While a peer views or controls the screen the host shows a desktop notice (`notify-rust`) naming it by twelve digits of its id, one per engagement however many short streams it opens; with `approval = "local"` a stream waits for `bohio gui allow ID` (or the notice's Allow action where the notification service has actions) on the node's local endpoint (`bohio-gui-approve/1`). `bohio_client::gui::Gui` and `bohio remote ... gui info|snapshot|click|move|scroll|type|key|clipboard`. Platform backends are a `gui::Desktop` each; Windows has one, below.
- The screen of a host's desktop as a stream of changes: `watch` on `bohio-gui/1` (`gui.view`). The host compares each capture in 64 pixel tiles, sends the changed rectangles (`zstd_rgb` where that costs under `lossless_max_bpp` bytes a pixel, JPEG where it does not, and a JPEG rectangle that stays unchanged for `refine_after` is sent again lossless) and never has more than `frames_in_flight` updates the client has not acknowledged, so nothing queues; acknowledgements that come late (beyond the least delay of the last `adapt_window`, so the link's round trip is not lateness) step the watch down a ladder of JPEG quality, frame size and update rate, and early ones step it back up. A client takes `Gui::watch` and `next_event` and keeps the frame in a `bohio_transfer::screen::Compositor` that refuses a rectangle outside the frame or past its limits; `bohio remote ... gui watch [--seconds N] [--stats] [--out DIR]` prints the rate, the bytes and the host's own measure of acknowledgement delay. New `[gui]` keys, each with its default in `examples/bohio.cfg`: `default_fps` (`5`), `max_fps` (`15`), `min_fps` (`1`), `tile` (`64`), `frames_in_flight` (`2`), `lossless_max_bpp` (`0.75`), `refine_after` (`1s`), `zstd_level` (`3`), `watch_quality` (`90`), `adapt` (`true`), `adapt_ladder`, `adapt_window` (`32`), `adapt_down_after` (`3`), `adapt_up_after` (`5`), `adapt_late` (`1.5`), `adapt_early` (`0.5`), `max_rate` and `max_rect_bytes` (`33554432`). `bohio-transfer` gains the `screen` module (feature `screen`), `bohio-client` the feature `screen` and `Error::Screen`, and `examples/gui_host.rs` serves a synthetic desktop for measuring a watch with the built command.
- Remote forwards: the host listens for a peer and hands it each connection (`ssh -R`), and every kind of end pairs with every kind on the other side. `bohio-listen/1` (a new `forward.listen` permission) has the host bind a TCP address (port 0 lets it choose), a Unix socket or a Windows named pipe, answers `listening` (what was bound, and a random 128-bit token) and then announces each connection that arrives (`arrival`: an id and its source); the listener lives exactly as long as that stream, so closing it, losing the link or a revoke ends the listener, closes what still waits and resets what was handed over. `bohio-accept/1` claims one arrival by the token and its id, answers `connected` or `not_found` (the same words for an unknown, expired, claimed or another peer's arrival) and then carries the connection's bytes as `bohio-connect/1` does. A peer binds only where its `[peer."<id>".forward] listen` list says (`bohio peer approve --listen RULE`, which also grants `forward.listen`): `BIND:PORT` with an address (`0.0.0.0` too), a CIDR network or `*` and a port, a range or `*` (the host-chosen port `0` only where a rule names it or `*`), and `unix:PATH` or `pipe:NAME` exactly or with `*` and `?`; a bind no rule covers is refused before anything listens. A socket the host creates is `0o600` and a pipe is for its own account, and `ipc_same_user` closes a connection from another account unread. `[forward]` gains `max_listeners` (`16`), `max_listeners_per_peer` (`8`), `max_pending` (`16`), `accept_timeout` (`10s`), `socket_mode` (`"0o600"`) and `ipc_same_user` (`true`); a new error code `in_use`; `info.forward.listen` lists the kinds. `bohio remote ... forward -R [BIND:]PORT=LOCAL | unix:PATH=LOCAL | pipe:NAME=LOCAL` (mixed freely with `-L`) brings each arrival to a TCP, Unix socket or pipe target on this machine, and `bohio remote ... listen [--keep] BIND` bridges one arrival (or each, with `--keep`) to standard input and output, with the address on standard error; both work over `--via`. `bohio_client::forward` has `listen`, `RemoteListener`, `RemoteForward`, `connect_local` and `Tunnel::pump_local`; `NodeEvent::Forwarded` tells each bind and claim. A Windows named pipe still has no half-close. `docs/protocol.md` has the CDDL and `vectors/listen.json` and `vectors/accept.json` the messages.
- Connections the host makes for a peer: local forwards, `connect` and `ProxyCommand`. `bohio-connect/1` (a new `forward.connect` permission) opens one connection from the host to a target (`tcp` host and port, a Unix socket, a Windows named pipe), answers once with `connected` (the address reached) or an error that says why nothing connected (`refused`, `unreachable`, `timeout`, `not_found`, `busy`, `unsupported`), and then carries the connection's bytes raw in both directions, a `finish` as a half-close and any other end as a reset. The host also serves `coqui-link`'s `tcp/1` under the same grant, so a `coqui-link` peer uses it unchanged. A peer reaches only what its `[peer."<id>".forward] connect` list names (`bohio peer approve --connect RULE`, which also grants `forward.connect`): `HOST:PORT` with an exact name, `*.suffix`, `*`, an address or a CIDR network and a port, a range or `*`, and `unix:PATH` or `pipe:NAME` exactly or with `*` and `?` that do not cross a separator; nothing is resolved to decide, so an address rule never matches a name. A target the grant does not cover is refused before the host connects, and the grant is asked again at every `[link] recheck`, so a revoke resets running connections. `[forward]` holds `enabled`, `connect_timeout` (`10s`), `max_connections` (`64`), `max_connections_per_peer` (`16`), `chunk_size`, `stalled`, the pump's `idle_min`, `idle_max` and `watch`, and the client's `listen_poll`, `answer_timeout` and `max_local_connections`; `info` reports `forward`. `bohio remote ... connect [--check] TARGET` bridges standard input and output (netcat, `ssh -o ProxyCommand="bohio remote ... connect %h:%p"`) and `bohio remote ... forward -L [BIND:]PORT=TARGET | unix:PATH=TARGET | pipe:NAME=TARGET` listens locally (loopback unless an address is named, which is reported as `non-default`); both work over `--via`. `bohio_client::forward` has `connect`, `Tunnel`, `listen_tcp`, `listen_ipc` and `ipc`; `NodeEvent::Forwarded` tells each connect (a target's text, never a byte). `bohio_client::Open::open` returns a `coqui_link::mux::LinkStream` (a `Relay` now finishes, says whether its peer finished and closes with a reason), so a half-close crosses the relay and the node's `--via` pass; an `Open` over plain channels wraps them in `relay::Plain`, and `Open::is_up` is new. A Windows named pipe has no half-close. `docs/protocol.md` has the CDDL and `vectors/forward.json` the messages.
- Hashing on the host, for pathapi's compare (its default is MD5) and any other sync. `bohio-hash/1` (needs `fs.read`) takes a request of algorithms in its open
  and a stream of items (`path`, `offset`, `length`, and `if_size` with `if_modified` to skip a file that has not changed), and answers each in order with its
  digests, or with an item error that does not end the stream; a long hash no longer holds the control stream and a batch is not held to `max_metadata`.
  Ten algorithms, chosen per call and several in one pass: `md5`, `sha1`, `sha256`, `sha384`, `sha512`, `blake3`, `xxh3`, `xxh128`, `xxh64` and `crc32c`, written
  as the reference tools print them. New crate `bohio-transfer` (`hash::{available, Hasher, digest_reader}`, no I/O of its own). `[hash]` has `max_streams` (`4`),
  `rate` (`0`, unlimited), `read_size` (`1048576`) and `algorithms` (every one); `[filesystem] write_hashes` (`["sha256"]`) is what a write answers. A write
  takes `expect` (a digest per algorithm, all checked) and `hashes`; a read takes `hashes` and its closing frame carries the digests of what it sent. `info`
  and `hello` report `transfer` (`hashes`, `hash_limits`). `bohio_client::hash::{hash_file, hash_range, hash_many, hash_items}` (items and results on two
  threads, so a long batch cannot stop on a full stream), `bohio remote ... hash [--algorithm NAME]... PATH...` and the bench's `hash_*` scenarios
  (feature `hash`). `docs/protocol.md` has the CDDL and `vectors/hash.json` the messages.
- Compression, per stream and per direction, for a slow link or a weak host. A client names it in the request (`compression` on a read and a write,
  `output_compression` and `stdin_compression` on exec; `zstd`, `lz4`, `deflate`, `none` or `auto`, with a `level` and for zstd a `window_log`); the host clamps it to its
  `[compression]` caps and reports what it used in the first frame, and `info.transfer` lists the algorithms with their levels, `compression_default` and `prepared`.
  Compressed bytes travel in their own frame tags beside the raw ones (`0x06` host to client, `0x14` write, `0x06`/`0x07`/`0x13` exec), so a sender switches per
  frame: a piece that does not shrink goes raw, and **a raw frame ends the compression context**, which every implementation follows (`docs/protocol.md`). A file
  whose extension is already compressed, whose name is key material (`exclude`) or whose first `sample_bytes` do not compress is read raw from the first frame.
  `prepare: true` compresses the whole range into a file on the host first (progress frames keep the stream alive), reports `compressed_length` and a `token`, and
  resumes from a compressed offset. What a peer sends is decoded within `window_log_max` and `max_expansion`, and a reader stops at the header's `length`.
  `[compression]` has `allowed`, `default`, `max_level`, `deflate_max_level`, `window_log_max`, `workers`, `skip_extensions`, `sample_bytes`, `sample_ratio`,
  `exclude`, `max_expansion`, `prepare_dir`, `prepare_max_bytes` and `prepare_ttl`. zstd is the C library behind the default-on Cargo feature `zstd` (`zstdmt` adds
  worker threads) of `bohio`, `bohio-client` and `bohio-transfer`; without it `lz4` and `deflate` remain and a request for zstd is `unsupported`.
  `bohio_transfer::compress` (`Encoder`, `Decoder`, `Caps`, `Bounds`), `bohio_client::fs::{put, PutOptions, ReadOptions, resolve_auto}`, `Writer::start_with`,
  `Reader::{compression, wire_bytes}`, `Exec::{start_with, compression}`, `bohio remote ... read --compress ALG[:LEVEL] [--prepare]`, `write PATH` (standard input to a
  file) and `exec --compress`, and the bench's `read_<corpus>_<size>[_<algorithm>]`, `write_...` and `exec_text_...` scenarios (feature `compress`).
- `[link] key_recheck` (unset: `2 x recheck`) is how often the link itself asks whether the peer's key is still accepted; it was always twice `recheck`. A stream whose link ended before its reader took what it held (a bulk read behind a slow reader) lost that and read as ended in order, not revoked: the opener now lets the reader take the rest and the stream's own end for at most `[link] send_limit`. A revoke found by that check, and not by the stream recheck, now reaches a running stream as a revoke: coqui-link 50c768d closes every open stream revoked before it ends the link. A `remote --via` read or exec that the check found first used to end with `the channel failed: the peer broke the wire format`.
- `tools/build.py` (a copy of the release overlay's build tool), `tools/build.cfg` and `tools/sdk.lock`: a `deps` branch of vendored
  crates kept equal to `Cargo.lock`, the lock of the toolchains and base images a release is built with, offline builds from the
  branch, and release archives per target (static Linux musl, Windows with a static CRT, a universal macOS binary) and a container
  image per architecture. `test.yml` checks the tool, builds offline with the network cut and builds every release artifact;
  `release.yml` attaches them to a GitHub release on a `v*` tag. See `docs/building.md`.
- Per-stream receive windows. One stream moves at most its window per round trip (1 MiB over a 250 ms path is about 4 MB/s), and the window could only be
  raised safely on both sides at once. `[link] bulk_window` is the receive window a side grants a bulk stream it receives (a client's `bohio-read/1`, a host's
  `bohio-write/1`): it widens the stream by granting credit, which every sender already accepts, so it may differ between sides and no peer changes. `max_window`
  (unset: the larger of `window` and `bulk_window`) bounds it and `auto_window` (`false`) grows a stream by itself from the link's round trip, up to it. `window`
  stays the credit both sides start from; each side logs once, as a warning and not a refusal, a `window` or `max_frame` its peer's `link/1` shows differing from
  its own. `bohio_client::Open` gains `open_with` and `bulk_window` (`OpenOptions { receive_window }`), `Opener::pair` takes the settings, and the host widens a
  `bohio-write/1` as it accepts it.
- `[link] max_metadata` (`4096`), `max_pending_opens` (`8`) and `max_opens_per_minute` (`600`) are settings, where coqui-link's defaults applied before: a sync
  that opens a stream for each small file is capped by the last. `tcp_send_buffer` and `tcp_receive_buffer` (unset: the system's automatic sizing) set a TCP
  socket's buffers before connecting and on the listener and each accepted socket.
- Pairing on a node's own listeners, over every transport: `bohio pair [--timeout T]` arms one PIN on the running node through its local control endpoint (`bohio-pair/1`), or, when no node runs, serves pairing alone on the configured `[[listen]]` entries (`--listen` only for a configuration with none). A joiner sends a marker message first (`coqui-link` 517c5db `pairing::join_shared`) and the node's `coqui_link::pairing::answer` runs a pairing or a proof by the first message, so a pairing needs no second port and runs over tcp, pipe, ws, wss, webtransport and serial. `bohio join` takes any endpoint `bohio remote` takes, with `--ca`, `--cert-hash`, `--clock-skew` and `--fallback`. A node pairs with `Node::with_pairing(store)` and `arm_pairing`; a paired key goes to `Keys::paired` (`LayeredPeers` writes its `[peer.<id>]` table, holding nothing); `NodeEvent::Paired` and `PairingRefused { source, attempts, reason }` never hold a PIN. The one-guess rule is now `[pairing]`: `max_attempts` (default `10`, `0` no limit), `attempt_delay` (`1s`, doubling per source to `attempt_delay_max`, `30s`), `pin_length` (`6`) and `timeout` (`5m`); `docs/security.md` has the odds. `peer::pair` and "pairing runs over tcp only" are gone.
- `bohio::node::Node`, an embeddable host: it is made from a `NodeConfig`, an identity, `Keys` (who is accepted) and `Grants`
  (what each may do) the caller supplies, and reads no file, environment variable or process-wide state, so an application runs
  one from settings kept anywhere. `MemoryKeys` and `MemoryGrants` are in-memory implementations whose changes apply at the next
  open or `[link] recheck`; `NodeEvents` (default `LogEvents`) reports link and stream events. `Config::node()` and
  `NodeConfig::validate` give and check the settings a node runs on.
- Either side may open streams on any link. `Node::connect` and `Node::connect_channel` dial a peer (its key pinned and proven before this
  node sends its own) and serve the link as an answered one is; every link a node serves runs with an opener, so `Node::peer(&id)` gives a
  `PeerLink` (an `Open`, cheap to clone) and `Node::links()` lists each link's peer, side, endpoint, source and start. `bohio_client::connect::{Opener, Opens}`
  are the open loop `Connection` already ran, now reusable, and `Connection::opener()` hands one out. Who dialed decides nothing: each side's own grants
  decide what the other may open, and a dialed key the node does not accept ends the link after the proof and is reported as a stranger.
- Roles are read from the link. A node's `link/1` `offers` now lists only the protocols its grant for that peer holds a permission for (it listed all
  five for any accepted key), so the document says what the node would serve that peer now. `PeerLink::offers(wait)` reads the peer's document,
  `LinkInfo::mine` gives this node's side, and `Opener::capabilities(wait)` reads it on the link's own thread. Admission still decides every open. Nothing
  is added to the wire; `docs/protocol.md` has a "Roles" section.
- A node dials out. A peer's table with an `endpoint` (`[peer."<id>"] endpoint = "tcp://host.example:7620"`, any endpoint `bohio remote` takes) makes
  `bohio serve` keep a link to that key, which the table's name pins and which must prove itself before this node sends its own; `[peer."<id>".dial]`
  (`DialConfig`) sets `ca`, `cert_hash`, `fallback`, `timeout` (`10s`), `retry_min` (`1s`), `retry_max` (`60s`), `retry_factor` (`2`) and
  `retry_jitter` (`0.1`). `Node::run_dial` is the loop, reporting `NodeEvent::Dialing` and `DialFailed`; a node with no `[[listen]]` may only dial.
  `[link] heartbeat` (`25s`, `0` off) and `heartbeat_misses` (`3`) make both sides of every link ask whether the other is there, so a path that goes silent
  without closing ends the link. `bohio peer approve --endpoint` writes the endpoint, `peer list` and `status` show it, `config check` counts the dials.
- Local control. A running node serves `bohio-via/1` and `bohio-links/1` on a local endpoint (`[control]`, by default `pipe://bohio-` and 16 hex digits of its id,
  this user alone; `bohio::local::{Local, LocalLink, Via}`), never on a peer's link. `bohio remote --via ID <action>` runs `info`, `exec`, `read` and `shell` over
  the link the node holds to that peer, whichever side made it, so the controller of a host that dials in is the node itself; `bohio links` lists each link with its side,
  endpoint or source and what each end offers. `bohio_client::connect::Opened` and `Relay::end` carry a stream's end reason and text so a refusal or a revoke crosses
  `--via` unchanged. `bohio_proto::local` has the wire types.

### Changed

- The link library is Cabuya (`cabuya`, renamed from `coqui-link`, same code, no alias). The dependency, every `coqui_link::` path and the docs name it, and the pairing marker a joiner sends first is `cabuya/pairing/1`; a peer that sends the old marker is not served. Earlier entries keep the old name.
- The last hard-coded waits, counts and sizes are settings with their old values as defaults: `[link] accept_wait`, `accept_poll` and `serial_reopen` (a listener's waits); `[pairing] pending`, `pending_per_source`, `ipv6_prefix` (the desk's bounds, which were the pairing crate's own) and `exchange_timeout` (a joiner that sends the marker and then nothing frees its place after `5s`, not the proof's `10s`); `[service] stop_wait` (Windows service start and stop); `[waiting]` (`per_source`, `total`, `rerecord`, `record_interval`, `ipv6_prefix`, `when_full`: the waiting list's bounds, which were the trust store's own defaults); and a new `[client]` section for the `bohio` command (`reply_timeout`, `transfer_timeout`, `gui_timeout`, `input_chunk`, `read_size`, `input_queue`, `probe_timeout`, `links_wait`), with `remote --reply-timeout`, `remote --transfer-timeout`, `links --wait` and `service uninstall --wait`. The library takes the same values: `link::Settings` gains the three listener waits, `SyncOptions` gains `read_size` and `compare_file` takes the options, `Gui::open_within` takes the wait, `ApprovalRequest` carries `poll`.
- `Node::serve_channel` applies `[link] max_connections` and, for a known source, `max_unproven_per_source`, as `serve_listening` does; a channel past one is refused at once.
- **Breaking, in place:** the control call `checksum` and its reply are gone (use `bohio-hash/1`); `write-request.expect_sha256` is `expect: {algorithm: hex}`
  and `write-done.sha256` is `hashes`; a read's closing frame (`0x04`) carries a body; `Fs::checksum` and `Checksum` are gone; `sha2` is 0.11.
- One layered `bohio.cfg` holds the peers; `peers.cfg` is gone (no reader kept). A peer is a `[peer."<id>"]` table, which
  accepts its key (even an empty one); `allow`, `fs_roots` and `[peer."<id>".exec]` say what it may do, and a table name that
  is not a peer id is refused. Without `--config` the system file is read and the user's merged over it, through `anycfg`
  (tables merge by key; arrays and scalars replace, so a higher layer can narrow a list); `--config FILE` (repeatable) or
  `BOHIO_CONFIG` name the layers instead, alone. `[service] check_access` and the new `user_layer` are read from the lowest
  layer only. Each layer is checked alone (an error names the file, line, column and key, never a value) and the merged value
  for ranges, naming the highest layer that sets the key. The `[peer.*]` tables are read again at every decision, so a hand edit
  of any layer applies at the next open or `[link] recheck`; a layer that cannot be read refuses every peer until it is fixed.
  The data directory keeps only the identity and the waiting list; the trust store's `accepted/` is no longer read.
  `bohio peer approve` takes any id and writes its table in place with `toml_edit` (the file's comments and layout stay) into the
  layer that holds it, else the last layer it can write, else a new user file; `peer revoke` removes it from every layer and names
  one it cannot write; `bohio pair` and `bohio join` write the other side's key into the configuration. `bohio remote` trusts the
  `[peer.<id>]` tables (or `--server`). On Unix a layer or its directory owned by another account than the running one or root, or
  writable by its group or others, is refused (`check_access = false` starts anyway); on Windows each layer and its directory get the
  rule the file and the data directory did. `config::Layers`, `Layered` and `policy::Peers` replace `Config::locate`,
  `Environment::config_candidates` and its configuration fields, and `Policies` and `PolicyError`; `ConfigError::Parse` gains `key`.
- `serve::Server` is replaced by `node::Node` (no alias), `serve::ServeError` by `node::NodeError`, `link::TrustPeers` by
  `link::NodePeers`, and `link::admission` and `link::grant_of` take `Grants` where they took the path of `peers.cfg`. The command
  supplies the two traits from its configuration layers (`peer::LayeredPeers`). `info::collect` takes a `NodeConfig` and the
  host's `PATH`.
- Choices the operator may make are no longer refusals; each keeps its strict default and says in the docs what it costs.
  `--fallback ENDPOINT` takes a `ws://` endpoint on any address (it used to be loopback only) and one on another host than the
  `webtransport://` endpoint; naming it is the choice. `tls_valid_days` takes any value from 1 (it was 1 to 14): a certificate valid
  longer than 14 days, or from files with a key that is not ECDSA P-256, is logged once at start as one a browser will not accept
  pinned by its hash, and other clients pin it by hash whatever its key or validity (`--cert-hash` no longer holds a WebTransport
  hash to the browser rule). A grant that lists `PATH` under `exec.env` lets a request set it (it was refused even when named).
  `[service] check_access = false` starts the host on Windows although another account may change its configuration file or data
  directory, and logs what was found; the default is still to refuse. `bohio-client`'s `Endpoint::with_fallback` no longer checks
  the host. Pins `coqui-transport-web` at the revision whose `Endpoints` takes these choices.

### Fixed

- The own desktop's X server is checked before the node sends it anything. The display's abstract socket name is host-wide, so another account could bind it first; the node now asks the kernel who listens (`SO_PEERCRED`) and refuses a server run by an account other than its own, naming both uids. `[source.native] own_session_check_server = false` serves whatever listens and is logged `non-default:`.
- `bohio gui-helper --stdio` needs no runtime directory. It built a placeholder `pipe://` endpoint that wants `XDG_RUNTIME_DIR`, which a login through `sshd` does not set, so the helper a node started through an ssh source exited at once on such a machine.
- Windows filesystem calls stay on handles. `list`, `readlink`, `mkdir`, `remove` (a tree too), `rename`, `symlink` and `set_attributes` no longer turn the parent's handle into a path and act on the path joined with the name: they open the name relative to the handle of the directory that holds it (`NtCreateFile` with `RootDirectory`, reparse points not followed) and act through the handle they get, so a directory swapped for a junction between two steps cannot redirect a call outside a root. A rename without `overwrite` is `FileRenameInfoEx` through the source's handle; `platform/winfs.rs` replaces `platform/rename.rs` in `tests/unsafe_files.rs`, and these calls refuse a name that holds a separator or a stream suffix.

- A caller that opens short streams in a row (a control stream opened and closed in a loop) is no longer refused with no progress because its own closes are still in flight: an open waits up to `[link] open_wait` (`250ms`; `0` fails at once) for one of the link's streams to end when it holds `max_streams`.
- The host's drain time (`[execution] drain_timeout`) no longer cuts the output of a process that has already ended while the reader is slow to take it; it still ends a descendant that holds a pipe open.
- Windows: a process `exec` starts, and the PowerShell the access check starts, hold only their three standard streams of the host. It used to inherit every inheritable handle, among them the sockets `TcpStream::try_clone` makes, so a connection the host had dropped stayed open until the process ended and then read as a reset (os error 10054) on the other side. A batch file is no longer started directly (its arguments would be read by `cmd`); run `cmd /C` on it.
- A configuration layer another account owns can no longer turn its own check off. `[service] check_access = false` in the lowest layer
  waived every finding, so on Windows any local user who created `%ProgramData%ohioohio.cfg` (every user may, while the folder does not
  exist) could write that line beside a `[peer.<id>]` table of their own and be served by every `bohio serve` and service that reads the
  system file. It now waives only paths the operator owns that others may change; a layer or directory another account owns is refused either way.
- A default layer that did not exist when `bohio serve` started was read at every decision once it appeared, and never checked: a system file
  another user made under `%ProgramData%` while the node ran chose its peers at once. A missing layer is now read while serving only when the
  nearest directory above it that exists passes the access check; otherwise it is read after a restart, which checks it.
- Every command checks the system file when it exists, as `serve` checks every layer: it names the data directory, where a client's key is
  made, and the control endpoint, so one another account made or every user may change is refused by `remote`, `join`, `id`, `pair` and `links` too.
- A client of a node's local control endpoint checks that it is served by this account before it sends anything (`bohio::local::Server`,
  `LocalLink::connect_to`, `Via::connect_to`, `ANOTHER_ACCOUNT`), unless `[control]` sets who may connect. The endpoint is not sealed, and
  another account that bound the name first (a pipe name is visible to every Windows user) read every `remote --via` request and could answer
  `bohio pair` with its own key as the one that paired; `pair` no longer falls back to serving alone when it meets one.
- `Node::run_dial` no longer dials a peer its `Keys` no longer accept: a peer revoked while the dialer ran kept being dialed until a restart,
  learning each time that this node was up, where it was and its key. It asks the keys again every `retry_min`.
- A pinned certificate made just now was refused at first and accepted later: a certificate is held to its dates even when pinned,
  and a client whose clock is behind the host's sees it as not yet valid until its clock reaches the start, while the message
  blamed the trust. The refusal now names the certificate's hash, its start or end and the clock difference;
  `bohio remote --clock-skew SPAN` (`ServerTrust::clock_skew`) accepts a start or end within SPAN of the client's clock (default
  none); the made WebTransport certificate's one-hour backdate is the setting `[[listen]] tls_backdate`. The message no longer
  holds a run of spaces. `--cert-hash` above is released from the browser rule, not from the certificate's dates.
- A grant narrowed while a stream runs now reaches it: a `bohio/1` stream reads the peer's grant again for every call, so
  taking away `fs.write` or a root applies to its next call (it used to keep the grant it opened with for as long as it
  stayed open), and the admission of an exec, a shell or a transfer checks that the program is still listed and the file
  still under a root, so such a stream ends at the next `[link] recheck`. `link::admission` takes the protocol, `link::covers`
  is the check, and `control::Context::current` is where the control stream reads the grant.
- On Windows `bohio serve` and the service refuse to start from a configuration file another account owns or every local
  user may change, and from a data directory every local user may change or read. Every user may create files and folders
  under `%ProgramData%`, where the service looks for `bohio\bohio.cfg`, so a local user could plant a configuration that
  chose the data directory, and with it the trusted keys and grants (running code as `LocalService`), or read the host's
  key from a data directory made there.
- One source, or one peer, can no longer hold every connection: `[link] max_unproven_per_source` (default 16) closes a
  connection unread when its source (an IPv4 address or an IPv6 /64) already has that many proving themselves, and
  `[link] max_links_per_peer` (default 16) closes a proven peer's link past that many. Before, anyone who could reach a
  listener could keep it from serving everyone by opening `max_connections` connections and sending nothing.
  `listen::Arrival::source` names a connection's source.
- A peer can no longer make a set-user-ID or set-group-ID file: a mode with `0o6000` in `set_mode`, `mkdir` or a write's
  `file_mode` is `denied`, and a `copy` or a `replace` drops those bits from the mode it keeps. Such a file, written by a
  peer that may only write under one root, ran as the service's account for any local user who started it.
- Under a program list a request may set or remove only the environment variables the grant names (`[peer.<id>.exec] env`,
  `bohio peer approve --env NAME`), never `PATH`: a peer allowed one harmless program could make it load a library of its own
  with `LD_PRELOAD` (or `DYLD_INSERT_LIBRARIES`, or run a file with `BASH_ENV`). `Grant::with_env`, `env_names` and
  `permits_env` are the grant's side.
- A program list (`exec.programs`) is now checked against what starts: each listed name is resolved on the host's own
  `PATH` to an absolute path and that path is spawned, and a request that sets or removes `PATH`, or clears the
  environment, is refused. A peer allowed `git` can no longer run its own `git` by pointing `PATH` at a directory it
  controls. `exec::Context` and `shell::Context` carry the host's `PATH` (`exec::Context::path`).

### Added

- `wss://` and `webtransport://` endpoints, to listen and to dial, for browsers and TLS-only proxies. The proof still decides who the
  host is; TLS only has to be accepted. A `[[listen]]` entry takes `tls_cert` and `tls_key` (PEM, read at start, never logged; `wss`
  needs both), and a `webtransport://` entry without them makes its own ECDSA P-256 certificate (`tls_valid_days`, 1 to 14, default
  13), prints `certificate sha256:... for ...` and makes a new one halfway through. `bohio remote` takes `--ca FILE` (roots instead of
  the system's) and `--cert-hash HASH` (a certificate trusted as it is) and, for a `webtransport://` host, `--fallback ENDPOINT`: a
  `ws://` (loopback only) or `wss://` endpoint of the same host, dialled when the QUIC path fails before anything crossed; a refused
  certificate never falls back. `bohio-client` has `dial::ServerTrust`, `Endpoint::dial_with`, `Endpoint::with_fallback`,
  `Endpoint::WebTransport` and `Connection::connect_with`; `bohio::listen` has `server_config` and `MadeCertificate`.
- `docs/protocol.md` is the wire for an implementer in another language: the carriers, the open metadata and CBOR messages of
  each protocol in CDDL, the one-byte frame tags, the error codes and the capability negotiation. `vectors/*.json` holds every
  message as hex, and `crates/bohio-proto/tests/vectors.rs` writes and checks them. `docs/security.md` covers the service's privileges
  against a peer's grants, container isolation, privileged deployments and the known limits; `docs/hostctl.md` maps a hostctl
  provider onto Bohío's calls.
- `packaging/systemd/bohio.service` runs the host as the unprivileged user `bohio` (`NoNewPrivileges`, `ProtectSystem=strict`, a
  writable data directory only, `KillMode=control-group`), and `packaging/container/Containerfile` builds a non-root image whose
  default command is `bohio serve --stdio`.
- `bohio service install|uninstall|run` runs the host as a Windows service (`windows-service`): `install` registers it to start
  automatically as `NT AUTHORITY\LocalService` (or `--account`), `uninstall` stops and removes it, and the service serves the configured
  `[[listen]]` endpoints until the manager stops it. The account must be able to write `[service] data_dir`.
- Every coqui transport carries the link: `pipe://` (Windows named pipes and Unix domain sockets, `coqui-transport-pipe`), `ws://`
  (WebSocket binary messages, `coqui-transport-web`), `serial://port?baud=N` (COBS frames with a CRC-32C, `coqui-transport-serial`) and
  standard input and output. `bohio serve --stdio` serves one link on standard input and output (for `docker exec -i`), and
  `bohio remote --command "program args"` or `stdio://program args` starts a program and uses its standard streams as the link.
  `[[listen]]` takes the settings of its scheme (`socket_mode`, `remote_clients`, `origins`, `baud`, `data_bits`, `parity`,
  `stop_bits`, `flow_control`), `bohio status` reports every configured endpoint, and `bohio-client` has `dial::Endpoint`.
  The proof and the grants are unchanged.
- The authenticated link over TCP, on `coqui-link`: `bohio serve` proves each peer (Noise by default) within `[link] proof_timeout` and
  serves its streams; a key that proves itself and is not accepted is recorded as waiting under its source address and refused. Each
  stream is decided from `peers.cfg` when it opens and every `[link] recheck` while it runs, so a revoke or a narrowed grant ends
  running processes, shells and transfers (the peer sees a `Permission` failure).
- Memory per link is bounded by `[link]` settings with documented defaults: `window`, `max_frame`, `max_message`, `queue_bytes`,
  `read_ahead`, `queued_bytes`, `send_limit`, `send_wait`, `poll_interval`, plus `max_connections` and `proof_timeout`. A 64 MiB file
  crosses the link in both directions with the host's resident memory growing by about 1 MiB.
- `bohio-client`: `connect::Connection` (a proven, owned `Open` over TCP or any coqui channel), `relay::Relay` (an owned, bounded channel over
  one stream of a link) and `link::Settings`.
- Commands: `bohio serve`, `status`, `id`, `peer list|approve|revoke`, `pair` (a PIN), `join` and `remote info|exec|read|shell`.
- Interactive shells (`bohio::shell`, `bohio-shell/1`): a shell kind from `info` or an explicit program on a
  pseudo-terminal (`portable-pty`: `openpty`, ConPTY), terminal output streamed raw, input, resize and kill frames, a
  bound on concurrent sessions (`[shell] max_sessions`), and the program's whole tree ended when the stream closes.
  `bohio-proto` has the shell request and frames; `bohio-client` has `shell::Shell`.

- `bohio-proto`: the wire types of protocol version 1 and their CBOR codec: control calls
  (`hello`, `info`), structured errors with a closed code list, the host's capabilities, shell kinds
  and the `bohio-exec/1` request and frames.
- `bohio` library: `bohio.cfg` configuration (unknown keys refused, every setting documented with
  its default, searched in `$BOHIO_CONFIG`, then the user's, then the system's location),
  `peers.cfg` per-peer grants (`info`, `fs.read`, `fs.write`, `exec`, `shell`, `admin`, filesystem
  roots, a program list), and the host's capabilities.
- `bohio config check` and `bohio info` (text or `--format json`); exit status 0, 1 or 2.
- Process execution (`bohio::exec::serve`): argv run directly or an explicit shell script, working
  directory and environment changes, standard input, streamed output and error, a deadline, kill and
  closed-stream handling that end the whole process tree, and a bound on concurrent processes
  (`[execution] max_processes`).
- `bohio-client`: the `Open` trait for a link and `exec::Exec` to run a process.
- Filesystem access confined to a peer's `fs_roots` (`bohio::fs`, `bohio::control`): `stat`, `list` (paged), `mkdir`,
  `remove`, `rename`, `copy`, `symlink`, `readlink`, `set_times`, `set_mode`, `set_attributes` and `checksum` on the control
  stream, and file streams `bohio-read/1` and `bohio-write/1` (atomic replace through a temporary sibling, or create, append
  and write at an offset). A `..` or a symbolic link that leaves a root is refused as `outside_root`, with every component
  resolved against a directory handle; the header states what is race-free on each operating system. New `[filesystem]`
  settings bound transfers, chunks, listing pages and idle time.
- `bohio-proto`: the filesystem calls, metadata and the transfer frames. `bohio-client`: `control::Control`, `fs::Fs`,
  `fs::Reader` and `fs::Writer`.
