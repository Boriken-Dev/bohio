# Security

Bohío exposes the operating system to peers it has proven. This page says what a peer can reach, what the service itself holds, where isolation stops, and the limits known today.

## Two sets of privileges

The service runs as one operating system account, and each peer holds a grant. They are different things, and the second never exceeds the first.

- **The service's privileges** are those of the account that runs `bohio serve`. Everything a peer does, a process it starts, a file it reads or writes, a shell it opens, happens as that account. A peer cannot do what the account cannot.
- **A peer's grant** is what its `[peer.<id>]` table in `bohio.cfg` says that key may do: `allow` (any of `info`, `fs.read`, `fs.write`, `exec`, `shell`, `admin`, `forward.connect`, `forward.listen`, `session`), `fs_roots` (the directories file operations are confined to), `exec.programs` (the programs it may start), `forward.connect` (the targets the host may connect to for it) and `forward.listen` (what the host may bind for it). A peer with no table, or no `allow`, holds nothing; a table, even an empty one, is what accepts its key. Being proven opens no stream; each stream is decided against the grant when it opens and again every `[link] recheck`, so a revoke ends what is running.

So the account bounds the worst case, and the grant narrows it. Run the service as an account that has only what its peers need, and give each peer the least that works.

A grant of `exec` or `shell` is the account's own authority: a peer that may start a program may do whatever that account may do with the program's arguments, and a peer that holds a shell holds that account's shell. `fs_roots` confines Bohío's file operations; it does not confine a process or a shell a peer starts, which can open any file the account can. Grant `exec` or `shell` only to a peer trusted with the account.

## Identities and pairing

A peer is a key, named by its id. Each side proves its key to the other before any stream opens. A node's key is in `identity` in its data directory (mode `0600` on Unix); the keys it accepts are its `[peer.<id>]` tables. A key that proves itself and is not accepted is recorded as waiting under its source address (only after its proof, and a bounded number per source and in all: `[waiting] per_source` 16 and `total` 1000, at most one new record a second from a source) and refused; the operator approves it with `bohio peer approve`. Because peers may grant a node rights of their own (see [Links in both directions](#links-in-both-directions)), the key file is worth what every peer grants that node, not only what it proves.

`bohio pair` arms a PIN on the listeners the node already serves (the running node through its local control endpoint, or the configured `[[listen]]` entries when none runs), so pairing needs no port of its own and runs over every transport the node listens on. A joiner tells the node it is pairing with a marker message before its handshake; a node with no PIN armed refuses it, and that refusal is an event. A paired peer holds nothing until the operator approves it with a grant. Nothing logs a PIN or a key: logs and events carry a peer id (a public value), a source address, an attempt count and a protocol name.

**Guessing odds.** The PIN has `pin_length` digits (default 6: 1,000,000 values) and lasts `[pairing] timeout` (default 5 minutes). It is used up by `max_attempts` wrong guesses (default 10), so a stranger who can reach the node guesses one armed PIN with probability `10 / 1,000,000`, one in 100,000, whatever the speed of the attack. A source that guesses wrong must then wait `attempt_delay` (default 1s), doubling at each wrong guess to `attempt_delay_max` (default 30s); a source that tries sooner is refused without a try, which does not count as a guess. From one source that is at most 10 guesses in about a minute, so the attempt count and not the delay is what bounds the odds. The count holds however many guesses run at once: a guess is counted when it begins its key exchange. A longer PIN divides the odds by ten for each digit. `max_attempts = 0` removes the count: the PIN then lasts until its timeout and the delay alone slows a guesser. The delay starts when a guess fails, and one source may run up to `[pairing] pending_per_source` guesses at once (default four, with `pending`, default 32, for the whole node), so one source gets about 60 guesses in the default 5 minutes (four at each step of 1s, 2s, 4s, 8s, 16s, then 30s), which is 60 in 1,000,000, and more for a stranger with many addresses (an IPv6 /64 counts as one source). Use it only where a trusted network reaches the node, or with a longer PIN and a short timeout. A joiner that is the operator's own and mistyped a PIN keeps the PIN until the tenth wrong guess.

While a PIN is armed, joiners that send the marker and then nothing hold the desk's places for up to `[pairing] exchange_timeout` each (default 5 seconds, not the proof's 10), and `[pairing] pending_per_source` (4) of them from one source, `pending` (32) in all. A stranger with eight addresses can still keep every place held by reconnecting every few seconds, which keeps the operator's own joiner waiting until the PIN ends; it gains no guess by it, and the cost to it is a connection each `exchange_timeout` from each address. Raise `pending` and `pending_per_source` to tolerate more, or lower `exchange_timeout` to free places sooner (a path slower than a few round trips then fails its pairing). With no PIN armed a joiner still runs the handshake and is then refused, which costs the node what a proof costs. A paired key is accepted and holds nothing: it may link, up to `max_links_per_peer` links, and read a `link/1` document that offers it nothing, until it is approved or revoked.

## Links in both directions

Either side of a link may open streams on it, and either may have dialed it. Who dialed decides nothing.

- **A link serves only keys a node accepts, whichever side dialed.** A node that dials a key it does not accept ends the link after the proof and records the key as waiting; a key that dials in is held to the same rule. Being dialed, or dialing, grants nothing.
- **Each side hosts what it grants and controls what it opens.** What a peer may do on a node is that node's grant for the peer's key, decided at every open and every `[link] recheck`, the same for a link either side made. A node that controls another is controlled by nobody unless it grants something, and what it may do on the other is the other's grant for it. The `link/1` document a node answers lists what it would serve that peer now; it is information, never authority.
- **A dial is pinned to its table.** `[peer.<id>] endpoint` makes the node dial that key and no other: the answering side must prove the table's id before the dialing node sends its own key (Noise, the default method, carries the dialer's key in its third message, after it has checked the answer). A DNS answer, a hijacked address or a wrong `endpoint` line therefore reaches something that cannot prove the key: the dial fails, nothing is served and the dialer's key is not shown. Under the WebCrypto method, a browser's, the dialer's first message carries its public key, so whoever answers learns which key is dialing, and still gains nothing.
- **A revoked peer is not dialed again.** A dialer stops while its keys do not accept the peer and asks again every `retry_min`, so a revoked peer learns neither that the node is up nor where it is. The endpoints dialed are read when the node starts: a changed or removed `endpoint` applies at a restart.
- **A dial's failures back off** from `retry_min` (1s) to `retry_max` (60s), each moved by `retry_jitter`. A peer that accepts the link and ends it after `retry_min` keeps its dialer at `retry_min`, one proof each time; only an accepted key can do that.
- **Heartbeats show a path observer that a link is alive.** Each side sends a ping every `[link] heartbeat` (25s), busy or not; its size and timing say that the link is there, never what it carries. `heartbeat = 0` turns them off, and a silent path is then noticed only when the next message fails.
- **An `endpoint` can start a program.** `stdio://program args` in a peer's table, or `--command`, starts that program as the node's account at every attempt. Whoever may write a layer may make the node run a program; that is one more reason every layer is checked (below).

## Configuration layers

The configuration is the system file with the user's merged over it, or the files `--config` names (`bohio serve` by itself, or the service). Whoever may write any layer decides who is accepted, what each peer may do, where the node dials (a program, for `stdio://`), the data directory (where the key is made) and the control endpoint.

- **Every layer is checked**, the file and its directory: on Unix one owned by another account than the running one or root, or writable by its group or others, is refused; on Windows one another account owns or every user may change. A higher layer can widen what a lower one grants, and a peer is accepted while any layer holds its table, so a narrow system file and a wide user file give the wide one.
- **`check_access = false`**, read from the lowest layer only, lets the node start from the operator's own paths that others may change, and logs each finding: then those others decide who connects. It never waives a layer or a directory **another account owns**: that account made it and could have written the line itself, so it is refused either way. This matters on Windows, where every user may create `%ProgramData%\bohio\bohio.cfg` when the folder does not exist yet.
- **Every command reads the system file**, the client's commands too (`remote`, `join`, `id`, `pair`, `links`), and the system file names the data directory and the control endpoint. Each command refuses a system file another account made, or one every user may change unless it says `check_access = false` and is the operator's. Files named with `--config` are the operator's choice and are checked by `serve` alone.
- **A layer that does not exist when the node starts** is read once it is made (a peer approved into a new user file applies at once), but only where no other account could make it: the nearest directory above it that exists must pass the same check. Otherwise, as for `%ProgramData%` with no `bohio` folder, a system file made while the node serves is read only after a restart, when it is checked like any layer.
- **Only `[peer.*]` is read live.** Every other section is read when the node starts.

## The local control endpoint

A running node serves `bohio-via/1`, `bohio-links/1`, `bohio-providers/1` (which libraries it loaded) and `bohio-pair/1` on `[control] endpoint`, a named pipe or a Unix socket. Whoever can connect may open, as this node, any stream any peer grants this node, list its links and arm a pairing PIN. The endpoint is not sealed, so it is guarded like the key:

- **Who may connect.** With no `socket_mode`, `socket_group` or `security_descriptor`, only this account may: the pipe or socket admits this user alone, and a client the system does not report as this user is closed unread. Setting any of the three replaces that with the operator's choice, and every account it admits holds all of the above.
- **Who is serving.** A client (`bohio remote --via`, `bohio links`, `bohio pair`) checks that the endpoint is served by its own account before it sends anything, and refuses another account's. A pipe name is visible to every user on Windows, so another account could bind it first while the node is down, and the node then runs without its control endpoint (it logs a warning); such an account would otherwise read every request (an exec's arguments, a file being written) and could answer `bohio pair` with a key of its own as the one that paired. With access settings in `[control]` the node may run as another account, and the client does not check: who may bind that name is then the boundary.
- On Unix the default socket is under `XDG_RUNTIME_DIR`, else `TMPDIR`; a directory others may write is refused by the node.

## Memory a peer can hold

Every buffer is bounded, but the bounds multiply. A proven peer with any grant can make a node hold, by not reading, up to `max_links_per_peer` links, each with `max_streams` streams, each with its receive window (`window`, 1 MiB; a host's `bohio-write/1` up to `bulk_window`; with `auto_window` up to `max_window`) plus two relay queues of `queue_bytes` (256 KiB). With the defaults that is 64 x 1.5 MiB, about 96 MiB a link, and about 1.5 GiB for one peer's 16 links; `max_connections` (128) bounds all peers together. A peer that is not trusted with that much memory needs a lower `max_links_per_peer` and `max_streams` on the node, or a node of its own. Unproven connections hold no more than one proof message each.

## Embedding

An application that runs a `bohio::node::Node` supplies its settings, identity, `Keys` and `Grants`; the node trusts them as given. [Embedding](embedding.md) shows how. What the API leaves to the application:

- **`Keys` decide who is a peer.** A `Keys` that accepts every key makes every key that proves itself a peer; `Grants` then decide what each may do, and `MemoryGrants` gives a key it has no entry for nothing. A question `Keys` cannot answer is `false`, and a `Grants` error refuses the stream.
- **`Keys::stranger` hears every proven key that is refused**, from anyone who can reach the node: bound what it keeps.
- **Bounds on connections are the node's.** `Node::serve_listening` and `Node::serve_channel` apply `max_connections` and `max_unproven_per_source` (for `serve_channel`, only when the caller passes the channel's `source`); `Node::connect_channel` dials a link the application chose to make, so it counts toward `max_links_per_peer` only.
- **`Node::serve_local_channel` checks nobody.** It serves the local protocols to whoever is on the channel; serve it only on an endpoint the application's own account alone can reach (`local::Local` does that).
- **`NodeEvents` run on the link's thread.** An event sink that blocks holds up that link.
- **A node starts with an empty `PATH`**: programs are looked for where `Node::with_path` says.

## What the program list does

`exec.programs` limits **which program starts**, not **what it does**. A list holding `git` lets a peer start `git`, and `git -c alias.x=!command` runs any command; `make`, `find -exec`, `xargs`, `ssh`, `docker` and every interpreter run anything they are given. List only programs that are safe with every argument a peer can give them, and treat a list that names a build tool or an interpreter as no restriction.

With a non-empty list, each name is resolved on the host's own `PATH` to an absolute path and that path is started, never what the request's `PATH` or working directory would find, and an explicit shell script is refused (a shell runs anything). A request may set or remove only the environment variables `exec.env` names (`bohio peer approve --program NAME --env VAR`), and may not clear the environment. `PATH` is a variable like any other, so it is refused until it is named; once named, the listed program is still the one found on the host's own `PATH`, but whatever it starts runs what the peer's `PATH` finds: a variable is as strong as an argument, since `LD_PRELOAD` and `DYLD_INSERT_LIBRARIES` load a library the peer chose into the program, and `BASH_ENV`, `GIT_SSH_COMMAND` or `PYTHONPATH` make it run code the peer chose. Name only variables that are safe with any value. The working directory is still the peer's choice, and some programs read their configuration from it (`git` runs `core.fsmonitor` from a repository's own config), so a program that does is as strong as its configuration. An empty list means any program and any environment.

## Hashing costs the host disk and CPU

A hash reads every byte it covers, so a peer that holds `fs.read` can make the host spend its disk and processor without moving a byte over the link. `bohio-hash/1` is bound by `[hash] max_streams` (4; a stream past it is `busy`), by `[hash] rate` (bytes a second per stream, unlimited by default), by `[hash] algorithms` (what the host computes: the cryptographic ones cost more than `xxh3` or `crc32c`) and by `[filesystem] idle_timeout`. Hashing needs `fs.read` and a root, each item is resolved against the grant as it is when it is reached, and a missing file or a path outside the roots is that item's error and reads nothing. A peer can learn a file's digest, so one that may hash may confirm a guess at its content: that is within what `fs.read` already allows. Every write and read that names digests spends the same CPU, and is held to the same algorithm list. `md5` and `sha1` are offered for comparing with existing sums and are not collision resistant.

## What a delta gives a peer

A delta moves less over the link and costs the host more work, and a delta write reads the file it replaces.

- **A delta write needs `fs.read` and `fs.write`.** Its copy steps read the target, and the `expect` digest of the new file, checked by the host, would tell a peer that may only write whether its guess about the target's content was right: so a peer with `fs.write` alone gets `denied` for a delta (a plain `replace` is still allowed), and the host's recheck ends a delta write whose peer lost `fs.read`. A delta read needs `fs.read` like any read, and a signature (`bohio-hash/1` with `blocks`) is a hash: what `fs.read` already allows.
- **A write is built beside the target and replaced atomically.** The new file is a temporary sibling, as for `replace`; the target is opened first and read through that handle, so a rename or a link swapped in between cannot make the copies read another file. The write is refused with `changed` when the target is not as the client saw it (size, modification time, optional digests) and checked again just before the rename, so a delta made against a file that has been replaced meanwhile does not overwrite the replacement. This is optimistic concurrency, not a lock: a writer that replaces the file between that last check and the rename wins the race.
- **What a peer can make the host spend.** A delta read holds the signature the client sends: `[delta] max_signature_bytes` (64 MiB; `busy` past it, decided from the sizes in the request before a batch is read) and a window of one block (up to `max_block`, 1 MiB). Matching reads the file once, a rolling checksum a byte at a time, and a strong hash for each weak match: it costs about what a hash of the file costs, and is bound by `[filesystem] max_transfers` as any transfer is. A delta write's copies cost the host disk reads and writes for a few bytes on the wire, so the output is bounded by `[delta] max_expansion` (1024 times the target's size plus what was received, once more than 1 MiB is produced; `0` turns it off, which is right only for a host that takes files that repeat a small base without limit) on top of the disk's own bound. A copy past the target's end is `bad_request`.
- **Compression composes.** Literal bytes are compressed as the stream says, with one context per stream direction as for any transfer; a copy frame carries no data and no secret. A read still sends a file whose name matches `[compression] exclude` raw.

## What a tree, a bundle and a resume give a peer

A walk, a bundle and a move are the same reads and writes in fewer streams, so they give a peer nothing a grant did not, and cost the host what the same work costs.

- **Every item is checked as it is reached.** A stream that carries many paths (a walk's roots, a bundle's items) is opened against the grant, but the paths come after the open, so the open cannot see them: each root and each item is decided by the peer's grant as it is then (read again from the layers, as a control call is), and a grant narrowed while the stream is open refuses the next one (`denied`, `outside_root`). Every path goes through the same roots and the same directory handle as a single read or write.
- **A walk reads directories and, with digests, files.** It is bound by `[walk] max_streams` (4) and `max_entries` (1,000,000 over a stream's roots), and a digest is paced by `[hash] rate`. A directory's names are held while it is listed, at most the entries left to send; the walk holds a few batches, never the tree. With `follow` a link is entered only where it stays under the root, a directory is entered once (by device and inode: a loop does not run it on), and a host that cannot tell directories apart does not enter a link to one.
- **A bundle holds one transfer slot** (`[filesystem] max_transfers`) however many files it carries, and ends past `[filesystem] max_bundle_items`. An item that fails alone costs the host the data it still reads and drops, so a failing item cannot desynchronize the one compression context. The stream's decoder is bound as a single write's is (`window_log_max`, `max_expansion`).
- **A move and a recursive copy are made on the host.** A move across filesystems copies and then removes; a copy that fails leaves the original, and a tree is bounded by `[filesystem] max_tree_entries`. A link inside a copied tree is copied as a link and only if its text still stays inside the roots; a device or a socket is refused. A rename or a move without `overwrite` no longer looks and then renames on Linux, macOS and Windows: the operating system refuses an existing target in the rename itself (`renameat2`, `renamex_np`, `MoveFileExW`), so a peer racing itself on two control streams cannot replace what it was told not to. On Windows the source is opened relative to its parent's handle and renamed through that handle into the target's parent (`FileRenameInfoEx`), so a directory renamed or swapped for a junction during the call cannot redirect it. Where none of these exists (FreeBSD and other Unix, or a filesystem that refuses the flag) a regular file is renamed with a hard link and an unlink, which has the same property; a directory, or a file on a filesystem without hard links, keeps the check-then-rename gap (everything involved lies inside the roots).
- **A resumable write keeps disk.** With `[filesystem] resume_ttl` above zero an interrupted `replace` leaves its temporary file, the size of what arrived, beside the target for that long (`resume_ttl` defaults to `0s`: none is kept). Only the peer that began it can continue it, for the same path: its name carries a hash of the peer and the path and a 128-bit token the host made, and anything else is `not_found` with the same words as an expired token. The kept file is removed once expired when the host starts (every root a peer is granted, up to `[filesystem] max_tree_entries` entries) and by the next resumable write in its directory. A peer that interrupts many such writes spends that disk; a host that does not want this keeps `resume_ttl` at zero.
- **`truncate` can extend a file** to any length the filesystem allows, which is the same disk a write could use.

## What search, `stats`, `which` and a follow give a peer

- **Search reads as `fs.read` does.** A search is a read of every file it opens, under the same roots and directory handle, and it never follows a link, so it reaches nothing a read of the same path would not. What it adds is the cost and the shape: a peer with `fs.read` can find a secret in a tree without downloading the tree, which a read-only peer could do before only by reading every file, and the host's disk and CPU pay for it. `[search] max_searches` (4), `max_file_bytes` (16 MiB, which is also the memory one search holds), `max_files` (100,000), `max_matches` (10,000), `max_line_bytes` and `deadline` (60 s) bound one search; the pattern's compiled size is bound by `regex_size_limit`, and matching is linear in the text whatever the pattern (the regex engine has no backtracking), so a hostile pattern costs a scan and not a stall. The host never logs a pattern (someone may be looking for a secret) and an error does not repeat it.
- **`stats` and `which` tell what the host is and has.** Both need `info`: the hostname, uptime, load, memory, the mounted disks with their sizes, and which programs are installed where. That is a map for choosing an attack on a host, so a peer that only reads files is not given it, and a compromised peer with `info` learns it without `exec`.
- **A follow is a read that does not end.** It reads what a read of the same file would, and keeps a stream open: `[filesystem] max_follows` (16) bounds how many, and none of them is a transfer slot. It stays on one file (or, by name, on whatever file the grant lets the path name), reading it again every `follow_interval`, and a revoke ends it within `[link] recheck`. A log that holds a secret written after the follow began is read as it is written, which a one-time read would not see; that is the point of the call, and a grant that allows the log allows this.

## What a forward gives a peer

`forward.connect` makes the host open connections for the peer, so the peer reaches what the host reaches, from the host's address: an internal service, a database, another machine's management port, and under a rule as wide as `*:*` a cloud metadata address or any address the host's network can route. A peer that holds it is as strong as the rules in its `[peer.<id>.forward] connect` list, which is why the permission alone allows nothing: a peer with no matching rule is refused before the host connects to anything, and a peer's grant of rules without the permission is refused the same way.

- **A rule is exact unless the operator wrote a pattern.** `HOST:PORT` names one target; `*.suffix`, `*`, an address range written as a CIDR network and a port range are the operator's choice, and each widens what a compromised peer reaches. Nothing is resolved when a rule is checked: an address or network rule matches only a target given as an address, so a name the peer supplies cannot be steered into a network by DNS, and a name rule trusts that name's DNS as any grant on a name does. To bind a grant to addresses, grant addresses.
- **A `unix:PATH` or `pipe:NAME` rule hands over what that socket or pipe is.** The container engine's socket is the engine's root, `/run/docker.sock` is a root shell, and a database socket is whatever its account may do. `*` and `?` in these rules do not cross a path separator, a path with a `..` part never matches, and a rule naming a directory's sockets (`unix:/run/user/*/bus`) grants every socket that directory ever holds. A named pipe is matched without case, as Windows compares them.
- **The bounds are settings.** `[forward] max_connections` (64, across peers) and `max_connections_per_peer` (16) bound how many connections a peer holds open, `connect_timeout` how long the host waits on a target, `chunk_size` and `stalled` how the pump moves bytes. A peer past a bound is told `busy`; none of them limits what a granted peer may reach. `idle_min`, `idle_max`, `watch` and `listen_poll` trade a forward's first-byte delay for the CPU an idle forward spends polling, and `answer_timeout` is how long a client waits for the host's answer; none of them widens a grant.
- **A forward is decided like any stream.** The grant is read when the stream opens and again every `[link] recheck`: a peer that loses the permission or the rule has its running connections reset, and the target sees a reset, not a clean end. The host logs a `forwarded` event (the peer, the target's text, how it went) and never a byte of what the connection carried.
- **The client side of `-L` gives the grant to whoever can connect.** `bohio remote ... forward -L` binds `127.0.0.1` unless another address is named, and says `non-default: bind ADDRESS` when it is not loopback: a process or a machine that reaches that port has what the peer was granted, with no proof of its own. A local socket or pipe is for this user alone (`0o600`); on a shared machine another account's program can still reach a loopback port.
- **A `tcp/1` forward is the same capability.** `bohio-connect/1` and `tcp/1` are served under one grant, so a `cabuya` peer does not widen what a peer may reach.

## What GUI access gives a peer

`gui.view`, `gui.input` and `gui.clipboard` are off for every peer until the owner grants them, and the host needs `[gui] enabled = true` besides. They give a peer the screen and the keyboard of the account that owns the desktop session:

- **`gui.view` reads everything on the screen.** Passwords shown in clear, one-time codes, messages, notifications with codes in them, other people's documents. A snapshot is not filtered, and an image that leaves the host cannot be taken back.
- **`gui.input` is the desktop user's whole authority.** It goes beyond what `exec`'s program list and `fs_roots` allow: whatever the user may click, type or approve, the peer may, including a program that is on no list and a prompt that asks for consent. Through a helper in the user's session it is the desktop user's authority, which may exceed the service account's.
- **`gui.clipboard` reads what a password manager just copied.** It needs `gui.view` or `gui.input` beside it, and every read is an event the owner hears.
- **What a screen shows is untrusted input to an agent.** A page, a message or a window title can carry instructions (prompt injection). Give each agent a key of its own, and a view-only grant to an agent that only needs to read.
- **A bridge hands the grant to whoever reaches it.** An MCP server or a protocol bridge on a peer's machine acts with that peer's grant for every program that can connect to it.
- **A locked screen refuses input by default.** Typing into a lock screen guesses the user's password; `[gui] input_when_locked` is for a host where that is the point. Snapshots still work: they show what the platform shows.
- **Rates are settings.** `max_streams` and `max_streams_per_peer` bound the streams, `snapshots_per_minute` the captures of a peer, `max_input_rate`, `max_batch_events`, `max_text` and `max_batch_wait` the input, `max_snapshot_pixels` the size of a capture and `clipboard_max_bytes` the clipboard. A zero is an error naming the key.
- **A watch is bounded on both ends.** The host sends at most `frames_in_flight` updates the client has not acknowledged and captures only when it may send, so a client that never reads holds `frames_in_flight` updates in flight (a frame at the worst, each rectangle at most `max_rect_bytes`) and no more; a stream at most `max_streams` of them. `max_fps` bounds the rate, `max_rate` the bytes a second, `tile` the rectangles. A client holds the frame a host describes only up to its own limits (`max_rect_bytes`, `max_snapshot_pixels`): it refuses a rectangle outside the frame, bytes longer than announced, a compressed rectangle that expands past its size, an image whose own size is not its rectangle's. The host grants the watch with `gui.view` and looks at the grant again every `state_interval`, besides the link's `recheck`.
- **The grant is decided at every request.** A narrowed grant refuses the next frame at once; the stream ends as revoked at the next `[link] recheck`.
- **The owner is told, and may be asked.** `[gui] indicator = "notify"` (the default) shows a desktop notice when a peer starts to view, to control, and when it stops; it names the peer by the first twelve digits of its id and carries nothing a peer wrote. The indicator informs and does not gate: where there is no notification service the notice is logged once and the stream goes on. `approval = "local"` makes a stream wait for the person at the desk (`bohio gui allow ID`, or the notice's Allow action where the service has actions) and is the setting that gates. What the person allowed is remembered for `approval_ttl` as the set of things they allowed (view, control, clipboard) for that peer and session: a peer allowed to view and then asking to control, or for the clipboard, is asked again, and the notice names the clipboard when it is asked for. `approval_ttl = "0s"` asks every stream. Both are off or on as the owner chooses: with `indicator = "none"` and `approval = "none"` a granted peer is on the screen without anyone at the desk knowing.
- **What the host tells its owner is counts.** `NodeEvent::Gui` carries the peer, the session, what was granted, how many snapshots, frames, input events and clipboard reads and writes there were: never pixels, typed text, key names or clipboard content.

## What the per-user GUI helper gives

A node that runs as a service has no desktop. `bohio gui-helper` is a process a desktop user starts at logon that connects out to the node and serves that user's desktop to the node's peers, so the service account and every peer holding `gui.view` or `gui.input` can see and drive an account that is not the service's. That is one account lending its whole session to another, so both ends check who the other is, by the operating system's answer about the connection and never by anything either side says:

- **The node serves only the accounts it lists.** `[gui] helper_accounts` (read from the lowest layer only) names them as SIDs or names on Windows and uids or names on Unix. The listener's access is wide on purpose (on Windows interactive users may connect, on Unix the socket is mode `0o666`), because an unlisted account must be able to connect to be refused: the connection of any other account, or one the system cannot name, is closed unread and `NodeEvent::Gui` says a connection was refused (with no account in it). A name is resolved to a SID or a uid when the listener binds, so a renamed account does not inherit another's place. On Unix the socket's directory must belong to the node's account and be writable by it alone, or the node does not start, because an account that can replace the socket can stand in for the node.
- **A helper on another machine is trusted by the login that reached it.** `[gui] source` (lowest layer only) starts
  `bohio gui-helper --stdio` (or the command the entry gives) through an exec source, normally an ssh source, and serves that machine's desktop as a session of the
  node. No account check applies, because there is no pipe whose owner could be asked: what authenticates the helper is the source's
  login (its host key check and its key), and the session is listed as `exec:SOURCE`. Anyone who can make that login reach another
  program gives the node a desktop it will serve to every peer holding `gui.view`, `gui.input` and `gui.clipboard`; a weaker
  `host_key_check` on the source weakens this too. The helper's own `[gui]` (on the machine) still narrows what the node allows,
  and the node's bounds still apply to each stream. The helper runs as the account the source logs in as, so it serves that
  account's session, and a session with no desktop answers `unavailable`.
- **A helper the node puts on the machine runs as the login's account, from a directory that account trusts.** `[gui] helper_upload` (lowest layer only) copies a file through a files source and runs it through an exec source, so whoever can make the node write another file there, or replace the file between the copy and the start, chooses the program the login runs. The node therefore refuses a directory another account can write to (`helper_upload_shared_dir = true` accepts one: any account that can write there can replace the helper before it starts, and a sticky directory such as `/tmp` is still refused), reuses a file only when its SHA-256 equals the node's own, and refuses to replace a different file of that name (`helper_upload_overwrite = true` replaces it, and then whatever sits under that name is lost). The platform check (`uname -sm` through the exec source, compared with the file's header) stops a helper that cannot run, not a hostile one: `helper_upload_check_platform = false` skips it, and a machine whose `uname` lies can say anything. The file is the node's own executable unless `helper_binary` names another, so that setting trusts the operator of the node and no one else.
- **The helper serves only the account it was told is the node's.** Before it sends anything, `bohio gui-helper` asks the system who serves the endpoint (on Windows the owner of the pipe object, on Unix the server's uid) and exits 1, naming who it found and who it expected, when that is not `--node-account`, `[gui] node_account` of the lowest layer, or `NT AUTHORITY\LocalService` on Windows and `bohio` on Unix. A name another account bound first, or a socket planted while the node was down, therefore receives nothing: not the hello, not a screen. On Windows the pipe's owner is the default owner of the token that made it, which for a service account is the account and for an elevated administrator can be the Administrators group (`S-1-5-32-544`), so `node_account` names whichever the node's pipe reports: trusting the Administrators group trusts every administrator.
- **The helper holds no key and reads no `[peer.*]` table.** It cannot tell a peer's grant from a forged one: the node decides each stream (the grant, `max_streams`, `max_streams_per_peer`, the snapshot rate, `approval = "local"` at the node) and sends the helper what it allowed, and the helper serves exactly that and never more. The node checks each input and clipboard frame against the grant as it is when the frame arrives, and a revoke ends the stream at `[link] recheck`, as for a node's own desktop.
- **The user's own `[gui]` only narrows.** The helper applies its user's `[gui]` (`indicator`, `approval`, `input_when_locked`, `max_input_rate`, `snapshots_per_minute`, `max_text` and the rest) beside the node's: the lower bound wins, `input_when_locked` is on only when both say so, and a notice is shown when either asks. Starting the helper is the user's consent to lend the desktop, so the user's `enabled` is not consulted. The notice appears on the user's own desktop, where the person is; the service node has none to show it on.
- **A helper that goes away ends its streams `unavailable`.** One helper serves one session of one account, and a second helper of that session replaces the first. A session is listed as `ACCOUNT:NAME`, the account being the system's answer and the name the helper's own, so no helper can take another account's session name.
- **What a helper reports is the helper's word.** The audit events a node re-emits for a relayed stream (counts only) come from the helper; a helper that lies about counts misreports its own user's session and nothing else. The node's own events say an open was refused.
## What a remote forward gives a peer

`forward.listen` makes the host open a port, a Unix socket or a named pipe for the peer and hand it every connection that arrives there. A peer that holds it is as strong as the rules in its `[peer.<id>.forward] listen` list, and the permission alone allows nothing, as `forward.connect` does.

- **A bind on loopback is open to every account of the host.** `127.0.0.1:PORT` is reached by any local user and any program of the host, with no proof of its own: they reach whatever the peer connects the arrivals to, on the peer's side, with the peer's own network position. `ipc_same_user` narrows this only for sockets and pipes. A port number is not a secret; give a peer `127.0.0.1:0` (the host chooses) or a short range, and bind nothing wider than the work needs.
- **A bind beyond loopback opens the host's network to the peer's side.** `0.0.0.0:PORT`, a LAN address or `*` is reached by every machine that can route to the host, and each connection is a connection to the peer's local target. The rule says it in the operator's own words (`0.0.0.0:8080` or `*:8080`); a peer with only a loopback rule is refused a wider bind before anything listens, and the client says `non-default: bind ADDRESS` when it names one.
- **A socket or pipe the host creates is for the host's own account.** A Unix socket is made with `[forward] socket_mode` (`0o600`) and a pipe with the access list of its creator alone, and `ipc_same_user` (default on) closes a connection from another account unread, as the operating system names it. A weaker `socket_mode` is the operator's choice and is logged; setting `ipc_same_user = false` leaves the mode, or the pipe's access list, as the only guard. A path is created only where `coqui-transport-pipe` finds no directory another account could use to replace the socket.
- **Claiming is by owner, not by secret.** A listener's token is random, but the host also checks that the stream claiming an arrival belongs to the peer that owns the listener, and answers an unknown, expired, claimed or another peer's token in the same words, so no peer learns another's listeners.
- **The bounds are settings.** `[forward] max_listeners` (16) and `max_listeners_per_peer` (8) bound listeners, `max_pending` (16, which a request's `backlog` may lower) arrivals waiting for one listener, `accept_timeout` (10 s) how long one waits, and a claimed connection holds one of `max_connections` and `max_connections_per_peer`. A peer past a bound is told `busy`, and a connection past `max_pending` is closed at once; none limits where a granted peer may bind.
- **A listener ends with its grant.** The grant is read when the stream opens and again every `[link] recheck`: a peer that loses `forward.listen` or the rule has its listener closed, the connections still waiting closed and the ones handed over reset, and the port or path is free again. The host logs `forwarded` events (the peer, the bind's text, how it went) and never a byte.
- **A remote forward can hand a socket to the host's other processes.** `-R unix:PATH=unix:/run/agent.sock` makes a socket on the host that reaches the peer's own agent socket (an SSH agent, a container engine): every process of the host's account that can open that path then acts through it. That is the credential forwarding this project does not offer as a feature (a host that can sign as the user can act as the user anywhere while the link lives); an operator who writes that rule has chosen it.
- **The client's `-R` gives its side to whoever reaches the host's port.** The local target of each arrival is the peer's own choice and is connected from the peer's machine, with its network position; a peer that connects arrivals to an internal service exposes that service to everything that reaches the host's bind.

## What a session gives a peer

`session` lets a peer start an `exec` program or a shell that keeps running when its stream ends, and attach to, list and end its own sessions later. It adds no program a peer could not already run (a session needs `exec` or `shell` and the program list applies at the start), and it adds time: a program runs until its linger (`[sessions] linger`, 24 h by default) after the peer is gone, with the peer's authority at the start of it.

- **A session outlives its peer's link, not its peer's grant.** The host looks at every session each `[sessions] check_every` (5 s) and ends one whose peer's key is no longer accepted or whose grant no longer holds `session` and the permission its kind needs (`exec` or `shell`); the program's whole tree ends with it. A peer that loses only a program list entry is not looked at again: the list is read when the program starts. A running stream is ended at the next `[link] recheck` as always.
- **A session is its owner's alone.** `sessions`, `attach` and `end_session` act on the caller's own sessions; another peer's id, and an id that does not exist, are answered in the same words (`not_found`). An `admin` lists every peer's sessions, with the owner's id, and may end them; it cannot attach to another's, which would show it that peer's output and typing. The one exception is a source's console, which is a shared session by design (see "The console is shared" below).
- **What a session keeps is output, in the host's memory.** A program's standard output, standard error or terminal bytes are held up to `scrollback` (1 MiB by default, a request may ask up to `max_scrollback`, 16 MiB), for as long as the session lives and, after the program exits, for `keep_exited` (1 h). Anything the program prints, a secret it reads and echoes included, is in that buffer and in the peer's reach until then; a terminal's buffer holds what the person typed that was echoed. Nothing is written to disk, and a session ends with the host.
- **The bounds are settings.** `max_detached` (16, across peers, the exited ones that are kept included) and `max_per_peer` (8) bound how many sessions exist, and each holds its `[execution] max_processes` or `[shell] max_sessions` slot while its program runs; a program that waits for its output to be taken (`pause`) holds that slot too. A peer past a bound is told `busy`.
- **Signals add nothing beyond `exec` or `shell`.** A peer that may run a program may signal the one it started; `interrupt`, `terminate`, `hangup`, `quit`, `user1` and `user2` go to the program's process group, and `kill` ends the tree.

## What a SOCKS listener and a jump give

`forward -D` and `--jump` are client compositions of the forwards above: they add no permission on a host, and what a host grants decides every target.

- **A SOCKS listener gives its grant to whoever reaches it.** The listener has no authentication (method 0): every program that can connect to it can ask the host for any target the peer's `connect` rules cover, as the peer. On loopback that is every account of this machine; another bind address is reported as `non-default: bind ADDRESS`. A name rule such as `*` covers every name and address the host can reach, a cloud metadata address included, so grant the narrowest rules a client of `-D` needs. Each client is a connection of `max_local_connections`; one that does not finish its handshake within `[forward] socks_timeout` (10 s) is closed.
- **A domain name is resolved by the host.** The client sends the name, not an address, so DNS answers from the host's position (the point of `--socks5-hostname`); a client that resolves names itself (`--socks5`) leaks its lookups and sends addresses. The host's name rules trust the host's DNS, as any name rule does.
- **A jump sees sealed bytes and who connects.** It carries the next hop's link as the payload of a `bohio-connect/1` stream, so it sees the next hop's address, the amount and timing of traffic, and which key dials, not the content or the key it proves. It grants `forward.connect` for the next address (or `exec` of one program for `stdio://`), which is what its operator can see in its own log. A hop is proven against the id the operator names: `--jump-server` for a jump and `--server` for the host, and a hop without one trusts the keys `bohio join` stored. A jump that answers instead of the next host (a wrong address, or a gateway that listens there itself) is refused by the proof.
- **A `stdio://` hop runs a program on the jump with this peer's authority there**, under the jump's `exec` grant and program list: a peer that may run `bohio serve --stdio` may run what the list names, nothing more.

## What an agent's tools give

`bohio mcp` and `bohio_client::tools` are not a new capability of a host: every tool is a call a person could make with `bohio remote`, decided by the host against the key's grant like any other, and a tool the grant does not cover answers `denied`. What they add is a caller that is a program reading text it did not write.

- **The server's caller is the agent, and the agent's input is untrusted.** A file it reads, a program's output, a page or a screen can tell it to do something else (prompt injection), and a call made on that word is made with the key's whole grant. The server cannot tell the agent's intent from what it was handed, so the grant is the only bound: one key per agent (its own `--config` and data directory), `exec` only where the work needs a program (an agent that reads needs `fs.read` and no more), `fs_roots` and `programs` as narrow as the work, and `session`, `forward.connect` and `forward.listen` only where the agent starts long programs or reaches services. A compromised agent has exactly its key's grant, for as long as the key is accepted; `bohio peer revoke` ends it within `[link] recheck`.
- **`exec` with a `script` is a shell.** The tool starts a shell of the host's kind with the agent's text. With a program list the shell has to be listed for it to work, and a listed shell runs anything it is told: once the list names a shell, it no longer narrows what the agent can do.
- **Files and forwards of the machine that runs the server need a flag.** `put` and `get` read and write files of this machine, which is more authority than the host's grant, so they are unavailable until `--local-root DIR` names the directories (a path is resolved with links followed and must lie under one). `forward_local` binds loopback here and refuses another address without `--forward-allow-remote-bind`: whoever reaches the port has the key's grant. `forward_remote` connects each arrival to a target of this machine, which only `--forward-local-target HOST:PORT` allows. Each flag is the operator's choice, and each widens what a prompt-injected agent can do from this machine, not only on the host.
- **A call that was started is never repeated.** The server makes the link to a host on first use and once more after a loss; a call that was running when the link was lost answers that it was, and the agent decides. Output is bounded (`--max-output`, and every size is a field of `Settings` with a ceiling), and an answer says when it cut something.
- **A server on standard input and output is as private as its parent.** The protocol has no authentication: whoever starts the process, or can write to its standard input, is the agent.

## Credential forwarding

Bohío does not forward a credential agent, and that is a decision, not a gap: a host that can sign as the user can act as the user anywhere while the link lives, so a compromised host would hold the user's reach into every machine that trusts the key, which no grant on the host can narrow. Jump hosts (`--jump`) remove the main need, since the client proves itself to each host and a gateway never holds a key.

An operator can still make one by hand, which is a visible choice: `-R unix:PATH=unix:/run/agent.sock` has the host listen on a socket that reaches the client's own agent socket (an SSH agent, a container engine), and every process of the host's account that can open that path then acts through it. The `listen` rule that allows the bind is the operator's word that this peer may do that; `ipc_same_user` and `socket_mode` keep other accounts of the host out, not the host's own. Do not write that rule for a host that is less trusted than the key behind the agent.

## What a kept forward costs

`[peer."<id>".forward] local` and `remote` make a node keep a forward up across link losses, so the exposure they describe is standing, not the length of one command.

- **A `local` entry is a port that stays open.** Its listener is bound when the entry is read and stays bound while the link is down and until the entry is removed; whoever can connect to it has what the peer was granted for that target, with no proof of its own. On loopback that is every program of every account of this machine, for as long as the node runs, not for as long as a person had a command open. An address beyond loopback is reported as `non-default` in the log and opens it to the network.
- **A connection that waits holds a slot.** While the link is down each connection a `local` listener accepts holds a thread, a socket and one of `[forward] max_local_connections` for up to `wait_for_link` (30 s); a client that opens connections faster than that closes them can fill the limit, after which a connection is closed at once. `wait_for_link = "0s"` closes a connection the moment there is no link; a longer wait hides a longer outage from a client that would have retried by itself.
- **A `remote` entry asks the host to listen again, and for the same port.** After a loss the request carries the port the host chose the first time, so the peer's `listen` rule must cover that port and not only `0`; a rule such as `127.0.0.1:*` allows every loopback port to that peer. Between the loss and the new link, another program of the host may take the port, which the request then reports as `in_use` until it is free; nothing guarantees the port back.
- **The host's bounds still hold, and a client waits at them.** A burst is served as `[forward] max_connections_per_peer` and `[link] max_pending_opens` drain, for up to `open_retry` (10 s) per connection; those bounds are what a peer costs the host, and are not raised by the retry.
- **Entries are read again as grants are.** Whoever can write the layer holding the peer's table can start a forward on this machine or have the peer's host listen for it; the layers are as protected as the `allow` lists beside them.
- **Over `--via` the node's link is not kept by the client.** A command through `bohio remote --via ID` is made again if the node's control endpoint is, but a connection that arrives while the node has no link to the peer is refused; a declared forward in the node's own file is what waits for the link.

## Compression costs CPU and memory, and what it must never mix

A peer that asks for compression makes the host compress (reads, exec output) and decompress (writes, standard input) for it. `[compression] allowed` is which algorithms the host will run; `max_level` (zstd, 19), `deflate_max_level` (9), `window_log_max` (23, 8 MiB: the window is the memory a decoder holds per stream, and an encoder at level 19 holds tens of MiB more) and `workers` are the cost of one stream, and `[filesystem] max_transfers` and `[execution] max_processes` still bound how many run. A host on a weak CPU allows `lz4` alone, or lowers the levels; a request above a cap is clamped and the stream's first frame says so. The control stream, shells and the proof are never compressed.

- **What a peer sends is decoded within bounds.** A zstd frame asking for a window above `window_log_max` is refused before memory is spent on it, and what a peer sends (a write, standard input) may not decompress to more than `max_expansion` times the compressed bytes received (1024; checked once more than 1 MiB has been produced), or the stream ends with `bad_request` and a `replace` leaves the target untouched. Both are the host's setting: `max_expansion = 0` turns the ratio check off and leaves the disk and `[filesystem]` bounds to stop a bomb, which is the right choice only for a host that must accept files of zeros. The client side has the matching bound: a reader stops when the decompressed bytes pass the header's `length`.
- **One context per stream direction.** A compression context is never shared between streams or directions, so bytes a peer chose cannot sit in the window of a context that also holds something secret (the attack on compressed-then-encrypted data that guesses a secret from the compressed size). A raw frame ends the context. A host does not compress key material in any case: `exclude` (key, certificate and password-store names by default) sends those files raw whatever the client asks.
- **Prepared reads** write a compressed copy of a file the peer may already read into `prepare_dir` (in the data directory by default, which belongs to the service's account alone: keep `fs_roots` away from it), named by a random 128-bit token bound to the peer that made it. Another peer's token, a malformed one and an expired one are all `not_found`; a resume re-checks that the path is still under the peer's roots; a file is removed when it passes `prepare_ttl`, by the next prepared read and when the node starts; one result is bounded by `prepare_max_bytes`. The host does not bound the sum of the prepared files: a peer may keep as many as it prepares within `prepare_ttl`, so a host short of disk lowers `prepare_max_bytes` and `prepare_ttl`.
- Compression is a request, not a negotiation: a host that does not allow an algorithm answers `unsupported` and a client picks another from `info.transfer.compression`.

## What a source gives a peer

A source is a path into the system the node is for, and **a peer reaches only each capability's default source** unless its
`[peer."<id>"]` table names more with `sources = [..]`; a source added to `bohio.cfg` later grants nobody anything. The check is
made when a stream opens and again every `[link] recheck`, so narrowing `sources` ends a console attach within it, and `info.access`
and the session list show a peer only the sources it reaches (a name it may not use is not even told).

A desktop helper that the node starts through an exec source (a session named `exec:NAME:...`) is behind that source: the peer must reach `NAME` like any other source (the default exec source, or `sources = ["NAME"]`). Another peer is not told the session, cannot open it by name or by default, and a frame of a stream whose grant lost the source is answered `denied`.

- **Power and media are separate permissions**, `power` and `media`, each off in the node until `[power] enabled` or `[media]
  enabled`. Switching a machine off is the owner's to grant; the image a machine boots decides what it runs. An agent gets only
  `power_status` and `media_status`: actions stay off the tool surface. The node's event names the peer, the source, the action and
  the outcome, and never an image or a URL (its query may be a credential). A source that outlives `action_timeout` finishes on
  its own thread and its answer is dropped.
- **An image of the node** (`media insert --path`) must lie under the peer's `fs_roots` and needs `fs.read`; the source reads it
  through the host from the confined file and from nothing else.
- **The console is shared.** A node's console of a source is one session every peer with `shell` and that source attaches to: a
  newer attach supersedes an older one, and what the far end echoes of what one peer typed (a password a serial login does not hide) is in the scrollback the next peer reads (`[sessions] scrollback`).
  Give a console only to peers that may see each other's session.
- **Secrets are references.** A setting a provider's schema marks sensitive (`#[schema(sensitive)]`) must hold `file:PATH`,
  `credential:NAME` or `keyring:SERVICE/ACCOUNT`; a literal is refused naming the key and never quoted. The `bohio` command reads
  `file:` references only from a file that no other account may read (mode `0600` and its owner, on Unix; no access entry for
  others on Windows) and `credential:` from a file of `$CREDENTIALS_DIRECTORY`, none larger than `[secrets] max_bytes` (`65536`);
  this build has no keyring and refuses `keyring:`. A secret is resolved when its source is built, held in a `Secret` that prints
  `[redacted]`, and handed to the provider, which then holds it: a provider's own care for it is the provider's.
- **What an ssh source gives a peer.** A peer holding `exec` or `shell` on an ssh source runs anything **the account the source logs in as** can
  run on that machine, and a peer holding the source's files reads and writes whatever that account can: the node's own grants (program
  list, roots) are decided on the node, but the machine's own permissions are the only limit behind them. The node holds the means to log in
  (an agent's signing, a key file, a password), so every peer that reaches the source acts as that account; give a source to a peer as you
  would give it that account. Under a program list the program is the one the host finds at that name on the account's `PATH`, not the node's.
- **`client = "openssh"` hands the login to the system's ssh program.** The source runs `ssh` as the node's account with the account's
  own `ssh_config`, agent and known hosts, in batch mode: the host key is checked by ssh (`strict` is `StrictHostKeyChecking=yes`,
  `tofu` is `accept-new`, `off` is `no` with no known_hosts file), a `host_key` pin is refused because ssh cannot check one, and
  `ssh_args` are the operator's own options. A `ProxyCommand` or `LocalCommand` in the account's configuration, or in `ssh_args`, runs
  as the node's account whenever a session starts: the configuration is as trusted as the source. A program the node starts under
  this client cannot be signalled (only killed by ending the ssh process), and a terminal's interrupt is the control byte.
- **Host-key checking weakens only by choice.** `host_key_check` is `strict` by default (the key is pinned by `host_key`, or is in
  `known_hosts`); `tofu` trusts the first key a host with no entry presents and holds it for the life of the source, so an attacker present at
  first contact is trusted; `off` accepts any key, so anyone on the path can pose as the host and be given every command, input and secret
  sent through it. Each weaker choice is logged at start as `non-default:`.
- **Limits are settings, and a larger one costs the host.** `max_channels` (default 8, below the server's 10) bounds the sessions one source
  holds open; raising it past the server's `MaxSessions` makes the server refuse the extra ones. `keepalive = "0s"` finds a dead connection
  only when something is sent on it. `operation_timeout`, `connect_timeout`, `exit_grace` and `reconnect_after` bound how long a stuck
  server holds a request; a larger value holds a node thread that long. A source that cannot connect is reported `unavailable` with the
  reason (never with a secret) and the node starts all the same.
- **What loading a library costs.** `[providers] paths` is empty by default, and then nothing is read or mapped. A library named
  there is the node's own code: it is mapped into the process, runs its initialisers and its provider calls as the account that
  runs the node (a service account, often with more rights than a user), with no sandbox, and a provider it offers can be named
  by `[source.<name>]` and reach what the node reaches. Loading is **unpinned**: nothing checks that the file is the one the
  operator meant, so **whoever can write the library file, or the directory it is in, as the node's own account (or root), chooses
  the code the node runs** (an account that can already edit `bohio.cfg` could name the library anyway, so this adds a way in only
  where the library path is writable by someone who cannot edit the configuration). By default a library or its directory that
  another account owns or may write is refused (`[providers] check_access`, only the lowest layer sets it). Setting it to `false`
  loads them without checking, and the node logs a `non-default:` line at start that `bohio providers` prints too: **another account that can
  write there then chooses the code the node runs**, so use it only where the directory's write access is held some other way
  (a read-only mount, a file system whose owner you cannot check). The check covers the file and the directory that holds it, not
  every directory above; a path whose parents another account can rename is outside it. A file is checked and then mapped, so a
  swap in between is possible for whoever may write there (which the check refuses). Only libraries that declare a Bohío kind
  are mapped; the declaration is the library's own claim, so it is a filter against loading unrelated files, not a proof of what
  a library is. The report holds each file's SHA-256 to compare against what you installed; pins that refuse a mismatch arrive
  once `guatiao` can check the bytes before it maps them. A statically linked musl build (the Linux release archives) maps them through the system's own `ld.so` and glibc, started inside the node: that
  adds the system's dynamic linker (or the file `[providers] ld_so` names, which only the lowest layer sets) to what the node
  runs, a C library that shares the process with the node's own, a handler on signal 33, and threads the node did not
  start. Its code has had no security review yet.
- **What starting a program costs.** `[[providers.program]]` is empty by default, and then nothing starts. A program named there
  is a child of the node, started as the account that runs the node with that account's environment (plus the entry's `env`,
  whose values are written in the configuration file and never logged), and a provider it offers can be named by
  `[source.<name>]` and reach what the node reaches through it. Starting is **unpinned**: nothing checks that the file is the
  one the operator meant, so whoever can write the program file, or the directory it is in, as the node's own account (or root),
  chooses the code the node runs. By default a program or its directory that another account owns or may write is refused
  (`[providers] check_access`, only the lowest layer sets it, as for libraries); `false` runs it and logs `non-default:`
  (`bohio providers` prints it too): use it only where the directory's write access is held some other way. The check covers the file and
  the directory that holds it, not every directory above, and a file is checked and then run, so a swap in between is possible
  for whoever may write there. A program is not a sandbox either way: it shares the node's account, files and network, and only
  its memory is apart, so a crash or a stuck call in it cannot take the node down (a call is bounded by `call_timeout`, a start
  by `start_timeout`, and a program that exits is started again at most `restart_limit` times in `restart_window`). A program
  that is restarted runs again with the same file and arguments. The report holds the file's SHA-256 to compare against what
  you installed. What the program writes to its standard error goes to the node's.
- **A library in a process of its own** (`[providers] isolate`, `isolated`) runs the same code as the account that runs the node,
  through a host program (`library_host`) that is itself code the node runs: both files and their directories are checked
  (`check_access`) and both are unpinned, so the cost is that of a program (above) plus the library's own. The process boundary
  keeps a crash, a leaked handle or a second C library out of the node and gives no isolation of rights: it is no sandbox, and
  the host may read and write whatever the node's account can. Nothing starts it but the configuration.
- **An ssh source's desktop is the machine's X display.** With `x11_display` set, a peer holding `gui.view` sees the machine's X screen
  and a peer holding `gui.input` types and clicks on it, as the account the source logs in as could; the cookie `xauth list` gives is
  read through the login and used only to connect. The node does not ask the machine's login session whether its screen is locked
  (the source `lacks` `lock_detection`), so the lock state is unknown, and input is refused (`unavailable`, "the lock state is not known") until `[gui] input_when_lock_unknown = true` says to type anyway, which is logged `non-default:` and then types at a lock screen like any window; the same holds for any desktop that cannot read the lock state (an X display with no logind, Wayland without it, WSLg). The own desktop reports `locked: false` and is not affected. The X socket's own permissions are the
  account's. The backend reaches the display through a loopback connection of the node, made and accepted in one step and bridged only
  if the connection that arrives is the node's own, so another account on the node cannot take it.
- **X forwarding gives a program on the machine the node's display.** `x11_forward = true` is an error unless `x11_trusted = true` is set too: untrusted forwarding (how `-X` restricts a client) cannot work in this build, because the X SECURITY extension has no binding in x11rb, so every forwarded program is a trusted one (as with `-Y`). With both set
  lets every program an ssh source starts connect to the node's X display as a trusted client: it can read every window, capture the
  screen, type into other programs and set the clipboard, as `ssh -Y` allows. The host's `sshd` gives each program a random cookie that
  the node checks (in constant time) and replaces with the display's own before the first byte reaches the display; a program on the
  machine that does not hold the cookie is closed. `x11_max_connections` (`64`) bounds the connections; one past it is refused.
  A peer that may start programs on the source (`exec`, `shell`) can therefore act on the node's desktop: give it the source only where
  that is acceptable. The node's own display is not reached by anything else through this.
- **Files on an ssh source are confined by path, not by handle.** A peer's `fs_root`s name directories **of the machine behind the source**
  and the node checks every path against them lexically, as it does for its own files. The source `lacks` `confined`: the server resolves
  each name on every call, so a symbolic link inside a root (one the machine has, or one the peer makes with `symlink`) can lead out of it,
  and a directory swapped for a link between two calls of one request is followed. The account the source logs in as is the only limit behind
  the roots: give a peer an ssh files source only where that account's own permissions are the confinement you want. `native` keeps its
  directory-handle guarantee. SFTP times are whole seconds and a server without `posix-rename@openssh.com` cannot replace a name in one step
  (the source says so and refuses it), so a replacing write that needs atomicity is refused there rather than made in two steps.

## Filesystem confinement

Every path resolves against a directory handle of a peer's `fs_roots`: `..` and an absolute path outside a root are `outside_root`, and so is a symbolic link that leaves a root, whether at the end of a path or in the middle. On Linux each lookup is one `openat2` with `RESOLVE_BENEATH` (kernel 5.6 and later), and elsewhere an `openat` walk that refuses to follow a link at each component, so a link swapped in while a call runs cannot lead out.

The root's owner is trusted: a hard link another local user makes to a file outside a root exposes that file, and a bind mount or junction an administrator places inside a root is part of the root.

## Container isolation

A container is a boundary only as strong as its runtime's configuration, and Bohío adds none to it.

- `bohio serve --stdio` inside a container, reached with `docker exec -i NAME bohio serve --stdio`, serves the container's own filesystem and processes. A peer's grant bounds what it asks for; the container bounds what that can reach. A peer with `exec` in a container can do what the container's user can do there.
- The image in `packaging/container/` runs as a non-root user with no extra capabilities. A container started with `--privileged`, extra capabilities (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`), the host's PID or network namespace, a mounted container-engine socket or a bind mount of the host's root hands that reach to every peer that may `exec` or `shell`, and Bohío cannot narrow it.
- Resource limits (memory, processes, CPU) are the runtime's. Bohío's `max_processes`, `max_sessions` and `max_transfers` bound how many things start, not how much they use.
- A shared kernel is shared: a peer that runs code in a container can attack the kernel. Where peers are not trusted with that, give each its own virtual machine.

## Privileged deployments

The risk grows with the account. A service run as `root`, `SYSTEM`, or any account in the `Administrators`, `docker` or `wheel` group, with a peer that holds `exec`, `shell` or `fs.write` outside a narrow root, gives that peer the machine.

- Prefer an unprivileged account. The systemd unit in `packaging/systemd/bohio.service` runs as `User=bohio` with `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true` and `PrivateTmp=true`, and writes only `StateDirectory=bohio`. `bohio service install` registers a Windows service as `NT AUTHORITY\LocalService`, which has no administrative rights (it does hold the right to impersonate, so a local user who could run code as it could go further).
- Whoever may change a configuration layer (the system file, the user's or any `--config` file) or the data directory decides who the host trusts and what each peer may do, and whoever may read the data directory holds the host's key; [Configuration layers](#configuration-layers) says how each layer is checked. On Windows every local user may add files and folders under `%ProgramData%`, and a folder made there inherits that, so `bohio serve` and the service refuse to start from a configuration file another account owns or every user may change, or from a data directory every user may change or read. Make `%ProgramData%\bohio` before installing the service and narrow its access list to the administrators, SYSTEM and the service's account (`icacls %ProgramData%\bohio /inheritance:r /grant:r *S-1-5-18:(OI)(CI)F *S-1-5-32-544:(OI)(CI)F *S-1-5-19:(OI)(CI)M`), or keep the default data directory in the service account's own profile.
- When a task needs more, widen it in the smallest way: a group that owns one directory, a command allowed through `sudo` for one account, a dedicated account for the deployment. Do not run the whole service as an administrator to let one peer do one thing.
- `fs_roots` set to `/` or a drive root, or a root that holds the account's own configuration (`bohio.cfg`, the `identity` key) lets a peer with `fs.write` change who else is trusted. Keep roots away from the data directory.
- A peer with `admin` is trusted to manage the host: it lists every peer's detached sessions and ends them (`sessions`, `end_session`), and nothing else needs it today. Grant it to nobody who should not see the program names and the owners of other peers' sessions, or end their work.
- A client's `--fallback ENDPOINT` after a blocked UDP path is dialled as named: a `ws://` one is plain until the proof has run (the proof then seals what follows, but a path observer sees the first messages and the carrier's metadata), and one on another host sends the proof to that host, so name only a host whose key you trust. A refused certificate never falls back.
- `tls_valid_days` and `tls_cert` are the operator's: a certificate a browser will not accept pinned by its hash (valid over 14 days, or not ECDSA P-256) is logged once at start and works for every other client, which pins it by hash alone.
- A certificate is held to its dates even when pinned by hash. One made just now by a host whose clock is ahead of the client's is refused, with the hash and the start time named, until the client's clock reaches its start: `tls_backdate` (default an hour) starts the certificate a host makes earlier, and `bohio remote --clock-skew SPAN` accepts a start or end within SPAN of the client's clock (default none; it weakens only the dates). A certificate from files is made by whoever made it: start it earlier than now.
- On Windows the host refuses to start when another account may change its configuration file or data directory; `[service] check_access = false` lets it start from paths the operator owns and logs the finding, and then who may change those paths decides who may connect. A path another account owns is refused either way.
- `ws://` is served without TLS beyond loopback, because the proof seals every message after it. A peer that reads the network sees metadata (message sizes and timing) and the source address, not content.
- `wss://` and `webtransport://` add TLS for browsers (mixed content, `serverCertificateHashes`) and for proxies that pass only TLS. They are not the host's identity: a client trusts the host by the proof, and the TLS certificate only has to be accepted by the client's trust (`--ca FILE`, `--cert-hash HASH` or the system's roots). A certificate a client is told to trust by hash is trusted whatever its name and issuer, so pass a hash only over a channel you trust. The host reads `tls_cert` and `tls_key` when it starts and never logs them; keep the key file readable by the service's account alone. A WebTransport listener with no `tls_cert` makes its own certificate (ECDSA P-256, 13 days by default), prints its hash and makes a new one halfway through its validity: a client or browser pinned to the old hash must be given the new one, so a host that browsers pin for long should use a certificate from files that something else renews. A WebTransport client's `--fallback` is dialled as named, `ws://` and another host included (see the fallback note above).
- A listener that is reachable is attackable: bind to the narrowest address, use a firewall, and prefer `pipe://`, `serve --stdio` or a loopback address behind a tunnel when a peer is on the same machine. `[link] max_connections` and `proof_timeout` bound what an unproven connection may cost; `max_unproven_per_source` keeps one address (or one IPv6 /64) from holding every slot while proving nothing, and `max_links_per_peer` keeps one proven peer from holding them with links. Behind a reverse proxy every peer has the proxy's address, so the per-source bound is shared by all of them there; many sources at once can still fill `max_connections`.

## Known limits

These are recorded and not fixed. Each is a platform limit, a window that needs a local attacker, or a bound on what cleanup can promise.

- **Ending a process tree is cleanup, not containment.** The host ends what a program leaves behind by accident; a peer that may run any program and means to leave one running can. On Unix a double fork with `setsid` leaves both the process group and the parent chain the host walks; on Windows a program can ask the WMI or Task Scheduler services to start one outside its job object. Such a process runs as the service's account until it exits, and while it holds the output pipe of the program that started it, one host thread waits on that pipe. Only a peer trusted with `exec` without a program list (or with a listed program that starts others on request) can do this; `KillMode=control-group` ends them with the unit.
- **A root is opened by its path.** On every platform the configured root is opened by its path once per call, so what lies above it is the administrator's to protect. On Windows `list`, `readlink`, `mkdir`, `remove`, `rename`, `symlink` and `set_attributes` act on the last name through the handle of the directory that holds it (`NtCreateFile` with `RootDirectory`, reparse points not followed, then `SetFileInformationByHandle`), as `stat`, hashes, reads and the opens of writes always did, so a local user who swaps a directory inside the root for a junction while a call runs cannot redirect it outside.
- **On Unix a chain of links a peer makes can lead out of its root for other programs.** Each link's target must stay inside the root by its words, but `sub/d` naming `..` and `esc` naming `sub/d/..` together name the root's parent, because the kernel resolves `..` after following `sub/d`. The host's own calls refuse such a path; a program that follows links in a root without a directory handle (a backup job, a web server serving it, a process a peer starts) does not. Do not point such a program at a root a peer may write.
- **A Windows shell session's process starts a moment before it joins its job object.** A program of `exec` starts inside its job (`PROC_THREAD_ATTRIBUTE_JOB_LIST`), so nothing it starts at once is outside the tree. A shell's pseudo-console starts its child itself, and the host puts it in the job as soon as the start returns: a process the shell starts in that instant is outside the tree and survives an ended session, a `kill` frame or a deadline.
- **A killed `serve` on Unix ends the trees it started, except what left their group.** Each program of `exec`, and each shell session, has a guardian: a small process in the program's group that waits on a pipe only the host holds the write end of. When the host dies (`SIGKILL`, the operating system's out-of-memory killer, power loss) the kernel closes the pipe, and the guardian signals the program's process group, and on Linux every process of a shell's session (a shell that gives each background job a group of its own keeps it out of the group; on macOS and FreeBSD such a job is not reached). `[execution] host_death` and `[shell] host_death` choose `kill` (the default), `term` (SIGTERM, which a program may ignore) or `leave` (the old behavior: the trees keep running). A process that left the group and session (a double fork with `setsid`) is out of reach and runs on; the systemd unit's `KillMode=control-group` ends it with the unit. A shell's guardian is made right after the shell starts, so a host killed in that instant leaves the session. A guardian that has ended is reaped by the process that adopted it: where the host is process 1 (a container's entrypoint), start the container with an init (`--init`), or each ended program leaves a zombie in the host's table. A Windows host's job object ends the tree when the process dies.
- **A serial line has one peer at a time, and a reconnect can lose a message.** The host opens the port, serves one link and opens it again about 250 ms later, discarding what arrived before. A client whose first message arrives before the host has reopened the port, such as a second `remote` right behind the first, is dropped and must try again. Each failed attempt costs the proof timeout.
- **`peer approve` and `peer revoke` edit a layer in place** (only the peer's table changes; the file's comments and layout stay) and replace the file atomically; two such commands at the same instant can lose one change. A layer the account cannot write is skipped by `approve`, and `revoke` names it: the key stays accepted there.
- **Only `[peer.*]` is read live.** Every other section is read when the host starts. A layer that cannot be read or parsed refuses every peer (logged once per distinct error) until it is fixed.
- **A revoked peer's link ends at its key check** (`[link] key_recheck`, twice `recheck` unset) at the latest; its streams end at the first recheck or at that check, whichever comes first, and either way the peer is told they were revoked. Between a revoke and that point a running stream goes on, and the node's own streams to that peer (`bohio remote --via`) may still be opened.
- **Two nodes that dial each other at the same moment hold two links.** Both serve, under the same grants, and each counts against `max_links_per_peer`; a dialer waits while one is up, so the pair settles at one once either ends.
- **The control endpoint's same-user check has not been tried against a second account on Windows.** The default access list admits this user alone, so the system refuses another account before the check is reached; a process of this account at a lower integrity level is refused by the label an elevated node adds. Any program this account runs may use the endpoint, as it may read the key.
- **A peer's text reaches the terminal as it is.** `bohio links` prints the protocol names a peer's `link/1` document offers and `bohio remote info` what a host reports, without removing terminal control sequences, so a peer can change how the operator's terminal shows them.
- **The data directory is not checked on Unix.** A data directory another account may write lets it replace the node's `identity`; keep it under the account's own home or `StateDirectory`.
- **A message or a key is never logged, but a process list is public.** `exec` argument vectors are not logged by the host; a program started on the host appears in that machine's process list with its arguments. `bohio join --pin` puts the PIN on a command line; without `--pin` it is read from standard input.
- **A service has no console.** A Windows service writes its diagnostics to standard error, which nothing reads; run the command in a terminal with `BOHIO_LOG` to see them. Under systemd they go to the journal.
- **A name rule trusts DNS.** An address or CIDR rule matches only a target given as an address, and nothing is resolved to decide, so a name the peer supplies cannot be steered into a network by DNS; a rule on a name (`db.example:5432`, `*.suffix`) is the host's resolver's word for where that name goes. To bind a grant to addresses, grant addresses.
- **A `unix:` rule matches the path as written, not the file it reaches.** The host connects to the path with the operating system's own rules, which follow links, so a link in a directory a peer can write (through `fs.write` and a root that holds it, or any local account) can send a connection that a rule on that path allows to another socket. Keep the sockets a rule names, and the directories above them, out of reach of the peers and accounts the rule is not meant for. The same holds for the path of a `listen` rule.
- **A `replace` against a `base` has a window.** The host checks the target through its root handle when the write opens and again just before the rename, and a change another writer makes between that second check and the rename is replaced. A client that needs more locks the file by another means.
- **A session ends with the host.** Sessions are kept in memory: a host that stops, restarts or is killed ends every session and its program, and the scrollback is gone. `[sessions] linger` bounds how long a session lives detached, not how long the host does.
- **A Windows named pipe has no half-close.** A forward to a pipe ends both directions when the client ends its own, so a pipe server that answers only after the end of its input gets none; one that answers each message works. A Unix socket half-closes.
- **One extra round trip per remote-forward connection.** The host announces an arrival and the peer opens `bohio-accept/1` to claim it, so a connection reaches its target one trip later than a local forward's: about 130 ms across a slow site-to-site VPN, which a keep-alive connection pays once.
- **A forward's reset reaches only what the pump can end.** A revoked forward is cut at the next `[link] recheck` (a connection already closed by the target has nothing left to cut), and a connection to a Unix socket or a pipe is ended by closing it, not by a reset, which those do not have.
- **A forward that is kept ends only with its entry.** A running bridged connection ends with its link, as before: a stream cannot be resumed on another link, so a client of a kept `-L` sees a reset and connects again (an SSH or database client usually does), and a connection that was made while the link was down is carried only from the moment the link is back.
- **A Windows `interrupt` of a program without a terminal needs a console the host shares.** It is a `CTRL_BREAK_EVENT` to the program's group; a host started with no console (a service, a process started detached) has none to send it through and answers `delivered: false`. `terminate` and `kill` end the tree through the job object either way.
- **A host started as a background job of a shell ignores `interrupt` and `quit` for the programs it starts.** A non-interactive shell starts `command &` with SIGINT and SIGQUIT ignored, and `nohup` ignores SIGHUP; a host started that way keeps them ignored, and the programs it starts inherit that, so `interrupt` does nothing to a program that does not install a handler (and a POSIX shell cannot trap a signal that was ignored when it started). Measured on an x86-64 Debian host: a node started with `nohup ... &` had SIGHUP, SIGINT and SIGQUIT ignored in its programs and a script's `trap ... INT` never ran; the same node started with `setsid -f` had only SIGPIPE ignored (as every Rust program does) and the handler ran. Start a host from a service manager, or detach it with `setsid -f`, and not with `&`.
- **A Ctrl-C typed at a pseudo-console does not reach a program when Ctrl-C is ignored in the host's process chain.** The ignore state of a console process is inherited by what it starts. Measured on the development machine: a test that types Ctrl-C at a ConPTY program reaches its handler when started from PowerShell, and does not when started from Git Bash, and does again when the starter clears the state (`SetConsoleCtrlHandler(NULL, FALSE)`) first. The host cannot see this and answers `delivered: true` for the byte it typed.
- **A session's output sent in the instant a link broke may not have arrived.** A host cannot tell which bytes a cut link had carried, so it keeps the newest output that was sent, up to `scrollback`, and forgets the oldest sent output first; a controller that reattaches names the last offset it read, and the output after it is there unless the program wrote more than `scrollback` bytes while nobody was attached and `on_full` is `drop_oldest` (`lost` says how many), or the program was paused with the buffer full of unsent output. Dropped output is counted, not kept. A session's streams are not compressed.
- **A loopback connect to a closed port in the ephemeral range can connect a socket to itself.** `bohio join` and the client refuse such a connection.
- **The Windows desktop backend serves the session the node runs in, and only while the screen is the person's own.** While the lock screen, a sign-in or an elevation prompt has the screen (the secure desktop, which a process in the user's session is refused: `OpenInputDesktop` answers access denied, measured on the development machine's own lock screen) capture and input are `unavailable` and say so; snapshots do not show the lock screen. Input is `SendInput`: it is injected into the person's session beside their own keyboard and mouse, so a person typing at the same moment interleaves with it, and Windows lets a program of lower integrity send to a window of higher integrity without reporting that it dropped the input (User Interface Privilege Isolation, as the platform documents it; not measured here: no elevated window was driven). Protected video may capture black (as the platform documents it; not measured here). A display that is rotated or in HDR is captured with GDI, not DXGI; GDI is slower on a large screen. The backend makes the process per-monitor DPI aware (v2) when it starts, which an embedding application that wanted another awareness has to set before. The clipboard's text is replaced while a peer sets it and is not put back; the clipboard history the operating system keeps may hold it.
- **The X11 desktop backend serves one X display, and what a display lets a client read.** Any client of an X display can read the whole screen and send input through XTest to any window on it, so the node needs the display's authority (`XAUTHORITY` or `~/.Xauthority`, which `x11rb` reads; the node's settings do not carry a cookie) and a peer with `gui.view` or `gui.input` has what that account has there. Input is XTest into the person's session beside their own keyboard and mouse. A character the keyboard has no key for is typed through a spare keycode that is bound to it for `x11_key_wait`: every program on the display sees the mapping change, and a program that reads the mapping late may miss the character. The clipboard is a selection this node owns while it runs (the text is gone when the node ends; `x11_selection` names which), and a text larger than one request to the display is refused rather than sent in parts. Lock detection is logind's `LockedHint` of the login session: a shell that belongs to no session (a login through `wsl.exe`, measured) has none, so `locked` is unknown unless the session is named (`x11_session`, or `XDG_SESSION_ID` which the command passes). A Wayland session's X display is refused unless `x11_in_wayland` is set. **Measured on WSLg** (WSL 2, XWayland of the WSLg compositor, on the development machine; local measurements, not a CI result): the display is one monitor (`rdp-0`, 1635 by 1090); `GetImage` of the root window answers `BadMatch` for every rectangle, even four pixels, so the backend builds the picture from the viewable top-level windows, bottom to top, over black, and what a snapshot holds is the X11 windows of WSL and nothing of the Windows desktop or of Wayland-only programs (the probe's own window was captured pixel for pixel, a region outside every window is black); a new window is placed far off screen (about -32730) until the compositor places it; XTest pointer motion, clicks, the wheel and key presses reached the probe window and the keyboard focus came with the window, in the runs that were made, except that in some runs made right after a build the pointer did not move at all (reported by `cursor`), which the test records as skipped; the XTest pointer is the X server's own and is not the person's pointer on the Windows desktop; logind answered for the session named `c1` and refused the process's own (`PID does not belong to any known session`). Two things are not measured: a second monitor (no private X server was available: the arithmetic is unit-tested and the live test is written, not run) and an Xvfb run.
- **The Wayland desktop backend (feature `gui-wayland`) serves a session through its desktop portals, and the portal's dialog is the operating system's approval.** A Wayland client cannot read the screen or send input to other programs; the portal asks the person at the desktop whether to share it, and what a peer holding `gui.view` or `gui.input` then has is what that person allowed: every monitor the portal gave (`persist_mode`, `multiple`), and with RemoteDesktop the keyboard and the pointer. The dialog appears at the first request that reaches the desktop; `info` reaches it only for a peer holding `gui.view` or `gui.input` (any other peer is told `enabled` and `formats` and nothing the desktop says), so a peer that may only ask `info` cannot make a dialog appear, but a peer that may look can; `wayland_retry` (`30s`) is how often at most after a refusal, and `wayland_persist = "none"` asks again at every session. `wayland_persist = "always"` keeps the portal's restore token in the data directory (`0600`): whoever reads that file and runs as that account can ask the portal for the same share without a dialog, so the file is as secret as the grant. The node takes the session bus of the account it runs as (`DBUS_SESSION_BUS_ADDRESS`, read by `zbus`, not by the node's settings), so a service account with no desktop session has no portal and says so. Input reaches the person's session beside their own and is refused while logind says the session is locked; where logind has no answer the lock state is unknown, as on X11. The cursor is hidden in the pictures. There is no clipboard. **Measured** (WSL 2 Fedora 44 aarch64, a headless sway 1.11 on a private D-Bus session and runtime directory, PipeWire 1.6.11, WirePlumber, `xdg-desktop-portal` 1.22.1 and `xdg-desktop-portal-wlr`; local measurements, not a CI result): the portal needs no click with `chooser_type=none`; `xdg-desktop-portal-wlr` has no RemoteDesktop interface (`org.freedesktop.portal.RemoteDesktop` does not exist on the bus), so the backend is a view and `input` answers `unsupported`; the compositor sends a picture only when the screen changes (the first picture of a session on a screen that does not change never came in 30 seconds, and a repaint of the background produced one), so a request waits `wayland_capture_wait` and then says so; the stream's buffers were mapped memory (`MemFd`) in `BGRx` at the output's size (1280 by 720), and a snapshot was the output's colour pixel for pixel. **Not measured:** GNOME's and KDE's portals (the dialog, RemoteDesktop input, the restore token), a scaled output, several monitors, a GPU buffer (a compositor that sends only those makes the stream `unavailable`), and any run on CI.
- **The macOS desktop backend serves the console session's screen under two grants a person gives.** The system guards the screen with Screen Recording and the event system with Accessibility, both given in System Settings, Privacy & Security, to a program at its path: the grant is the operating system's own approval of what `gui.view` and `gui.input` then pass on, so a peer holding them has what the logged-in user has, and the grants are the user's to withdraw at any time (a snapshot then answers `unavailable` at once). A moved or replaced `bohio` is a different program and is refused until it is allowed again, and the terminal that starts it may be the program the system asks about. A node started where there is no window server session (an ssh login, a LaunchDaemon, no one logged in) has no screen and says so; it does not prompt. The pointer and the keys are posted at the HID tap, beside the person's own, and a character is typed as itself whatever the layout. A pixel is put on the point that holds it (pixel over scale, rounded down), so on a Retina display two neighbouring pixels may be one point. Snapshots need macOS 14; the screen is captured whole and cut to the region, so a small region costs a whole capture. Measured on a macOS 15.7.7 x86_64 virtual machine with no Metal, reached by ssh (local measurements, not a CI result): with no one logged in the session dictionary is absent, `gui info`'s state is `unavailable` with that reason, `CGPreflightScreenCaptureAccess` is false and enigo's trust check fails, so a capture and an input request answer `unavailable` naming the pane and the test binary's path (`tests/gui_macos.rs`), and the pasteboard cannot be opened. Not measured: ScreenCaptureKit with a grant (with and without Metal), the lock state, a second display, a Retina scale, input and the pasteboard in a session, the wheel's direction under natural scrolling, and the pane's name on macOS 15 (`Screen & System Audio Recording`, as Apple documents it).

- **A service account's own desktop is the account's authority, not a person's.** With `own_session` a node serves a headless compositor and X server that the account's own user units run (`packaging/systemd/own-desktop/`). There is no person at it: no notice is seen, no `approval = "local"` can be answered, and no lock screen exists (`locked` is `false` and `lock_detection` is `false`, always). A peer holding `gui.input` there has what the account can run: whatever it types or clicks goes to the programs the account runs on that display, a terminal among them if one is open, so grant it as you would `exec` for that account. A peer holding only `gui.view` sees what those programs show, which may include secrets they display. The display is for the account alone: Xwayland admits the account that started it (its server-interpreted `localuser` entry; measured, a connection from another account is answered `Authorization required, but no authorization protocol specified`), is started with `-nolisten tcp`, and listens on an abstract socket whose name is host-wide: any local account can open it, none can use it without that entry, but any account that binds the name first would stand in for the server. The node therefore asks the kernel who listens (`SO_PEERCRED` on the connection) and refuses a server run by an account other than its own, naming both uids; `[source.native] own_session_check_server = false` serves whatever listens, is logged `non-default:`, and then sends what peers type (an agent's passwords) to, and takes pictures from, whichever local account won the race at boot or at an Xwayland restart. The node refuses a runtime directory that is not the account's own, not mode 0700, or a link, and names it; it does not run the compositor (`systemd` does, as the account, so a crash restarts it), and `info` names the display and the unit to look at when the display does not answer. The system unit has `ProtectHome=read-only`, not `true`: `true` hides `/run/user` and the node could not check the directory. The units and `sway.conf` live in the account's home, which the node's sandbox may write (`ReadWritePaths`): a peer that holds `exec` or `fs.write` for the account can change them and so what runs at the next start, as it can anything else the account owns. `install.sh` creates an account, enables lingering and installs a system unit: it is an administrator's step, never run by the node or its tests. **Measured** (WSL 2 Fedora 44 aarch64, sway 1.11 on its headless backend and Xwayland 24.1.15, under the development account's own user manager with the units renamed; local measurements, not a CI result): a snapshot of the whole root window is the probe's pattern pixel for pixel (a rootful Xwayland, unlike WSLg's rootless one, answers `GetImage` of the root), a click arrives at its root point, and ASCII, a shifted capital, a character the keyboard has no key for and a control combination arrive as keys; the same holds in a user-manager unit with `ProtectHome=read-only`, `PrivateTmp`, `ProtectSystem=strict` and `PrivateUsers`; `/run/user/UID` is not reachable under `ProtectHome=true`. **Not measured:** the system unit and `install.sh` on a real host (a real lingering system account), the portal target with PipeWire, WirePlumber and the portals in the account's own user manager, a GPU, and more than one output.
