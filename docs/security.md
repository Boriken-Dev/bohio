# Security

Bohío exposes the operating system to peers it has proven. This page says what a peer can reach, what the service itself holds, where isolation stops, and the limits known today.

## Two sets of privileges

The service runs as one operating system account, and each peer holds a grant. They are different things, and the second never exceeds the first.

- **The service's privileges** are those of the account that runs `bohio serve`. Everything a peer does, a process it starts, a file it reads or writes, a shell it opens, happens as that account. A peer cannot do what the account cannot.
- **A peer's grant** is what its `[peer.<id>]` table in `bohio.cfg` says that key may do: `allow` (any of `info`, `fs.read`, `fs.write`, `exec`, `shell`, `admin`, `forward.connect`), `fs_roots` (the directories file operations are confined to), `exec.programs` (the programs it may start) and `forward.connect` (the targets the host may connect to for it). A peer with no table, or no `allow`, holds nothing; a table, even an empty one, is what accepts its key. Being proven opens no stream; each stream is decided against the grant when it opens and again every `[link] recheck`, so a revoke ends what is running.

So the account bounds the worst case, and the grant narrows it. Run the service as an account that has only what its peers need, and give each peer the least that works.

A grant of `exec` or `shell` is the account's own authority: a peer that may start a program may do whatever that account may do with the program's arguments, and a peer that holds a shell holds that account's shell. `fs_roots` confines Bohío's file operations; it does not confine a process or a shell a peer starts, which can open any file the account can. Grant `exec` or `shell` only to a peer trusted with the account.

## Identities and pairing

A peer is a key, named by its id. Each side proves its key to the other before any stream opens. A node's key is in `identity` in its data directory (mode `0600` on Unix); the keys it accepts are its `[peer.<id>]` tables. A key that proves itself and is not accepted is recorded as waiting under its source address (only after its proof, and a bounded number per source) and refused; the operator approves it with `bohio peer approve`. Because peers may grant a node rights of their own (see [Links in both directions](#links-in-both-directions)), the key file is worth what every peer grants that node, not only what it proves.

`bohio pair` arms a PIN on the listeners the node already serves (the running node through its local control endpoint, or the configured `[[listen]]` entries when none runs), so pairing needs no port of its own and runs over every transport the node listens on. A joiner tells the node it is pairing with a marker message before its handshake; a node with no PIN armed refuses it, and that refusal is an event. A paired peer holds nothing until the operator approves it with a grant. Nothing logs a PIN or a key: logs and events carry a peer id (a public value), a source address, an attempt count and a protocol name.

**Guessing odds.** The PIN has `pin_length` digits (default 6: 1,000,000 values) and lasts `[pairing] timeout` (default 5 minutes). It is used up by `max_attempts` wrong guesses (default 10), so a stranger who can reach the node guesses one armed PIN with probability `10 / 1,000,000`, one in 100,000, whatever the speed of the attack. A source that guesses wrong must then wait `attempt_delay` (default 1s), doubling at each wrong guess to `attempt_delay_max` (default 30s); a source that tries sooner is refused without a try, which does not count as a guess. From one source that is at most 10 guesses in about a minute, so the attempt count and not the delay is what bounds the odds. The count holds however many guesses run at once: a guess is counted when it begins its key exchange. A longer PIN divides the odds by ten for each digit. `max_attempts = 0` removes the count: the PIN then lasts until its timeout and the delay alone slows a guesser. The delay starts when a guess fails, and one source may run up to four guesses at once (the pairing desk's own bound, with 32 for the whole node), so one source gets about 60 guesses in the default 5 minutes (four at each step of 1s, 2s, 4s, 8s, 16s, then 30s), which is 60 in 1,000,000, and more for a stranger with many addresses (an IPv6 /64 counts as one source). Use it only where a trusted network reaches the node, or with a longer PIN and a short timeout. A joiner that is the operator's own and mistyped a PIN keeps the PIN until the tenth wrong guess.

While a PIN is armed, joiners that send the marker and then nothing hold the desk's places for up to `proof_timeout` each, so a stranger with eight addresses can keep the operator's own joiner waiting until the PIN ends; it gains no guess by it. With no PIN armed a joiner still runs the handshake and is then refused, which costs the node what a proof costs. A paired key is accepted and holds nothing: it may link, up to `max_links_per_peer` links, and read a `link/1` document that offers it nothing, until it is approved or revoked.

## Links in both directions

Either side of a link may open streams on it, and either may have dialed it. Who dialed decides nothing.

- **A link serves only keys a node accepts, whichever side dialed.** A node that dials a key it does not accept ends the link after the proof and records the key as waiting; a key that dials in is held to the same rule. Being dialed, or dialing, grants nothing.
- **Each side hosts what it grants and controls what it opens.** What a peer may do on a node is that node's grant for the peer's key, decided at every open and every `[link] recheck`, the same for a link either side made. A node that controls another is controlled by nobody unless it grants something, and what it may do on the other is the other's grant for it. The `link/1` document a node answers lists what it would serve that peer now; it is information, never authority.
- **A dial is pinned to its table.** `[peer.<id>] endpoint` makes the node dial that key and no other: the answering side must prove the table's id before the dialing node sends its own key (Noise, the default method, carries the dialer's key in its third message, after it has checked the answer). A DNS answer, a hijacked address or a wrong `endpoint` line therefore reaches something that cannot prove the key: the dial fails, nothing is served and the dialer's key is not shown. Under the WebCrypto method, a browser's, the dialer's first message carries its public key, so whoever answers learns which key is dialing, and still gains nothing.
- **A revoked peer is not dialed again.** A dialer stops while its keys do not accept the peer and asks again every `retry_min`, so a revoked peer learns neither that the node is up nor where it is. The endpoints dialed are read when the node starts: a changed or removed `endpoint` applies at a restart.
- **A dial's failures back off** from `retry_min` (1s) to `retry_max` (60s), each moved by `retry_jitter`. A peer that accepts the link and ends it after `retry_min` keeps its dialer at `retry_min`, one proof each time; only an accepted key can do that.
- **Heartbeats show a path observer that a link is alive.** Each side sends a ping every `[link] heartbeat` (25s), busy or not; its size and timing say that the link is there, never what it carries. `heartbeat = 0` turns them off, and a silent path is then noticed only when the next message fails.
- **An `endpoint` can start a program.** `stdio://program args` in a peer's table, or `--command`, starts that program as the node's account at every attempt. Whoever may write a layer may make the node run a program; that is one more reason every layer is checked (below).

## Configuration layers

The configuration is the system file with the user's merged over it, or the files `--config` names (`bohio serve` by itself, or the service). Whoever may write any layer decides who is accepted, what each peer may do, where the node dials (a program, for `stdio://`), the data directory (where the key is made) and the control endpoint.

- **Every layer is checked**, the file and its directory: on Unix one owned by another account than the running one or root, or writable by its group or others, is refused; on Windows one another account owns or every user may change. A higher layer can widen what a lower one grants, and a peer is accepted while any layer holds its table, so a narrow system file and a wide user file give the wide one.
- **`check_access = false`**, read from the lowest layer only, lets the node start from the operator's own paths that others may change, and logs each finding: then those others decide who connects. It never waives a layer or a directory **another account owns**: that account made it and could have written the line itself, so it is refused either way. This matters on Windows, where every user may create `%ProgramData%\bohio\bohio.cfg` when the folder does not exist yet.
- **Every command reads the system file**, the client's commands too (`remote`, `join`, `id`, `pair`, `links`), and the system file names the data directory and the control endpoint. Each command refuses a system file another account made, or one every user may change unless it says `check_access = false` and is the operator's. Files named with `--config` are the operator's choice and are checked by `serve` alone.
- **A layer that does not exist when the node starts** is read once it is made (a peer approved into a new user file applies at once), but only where no other account could make it: the nearest directory above it that exists must pass the same check. Otherwise, as for `%ProgramData%` with no `bohio` folder, a system file made while the node serves is read only after a restart, when it is checked like any layer.
- **Only `[peer.*]` is read live.** Every other section is read when the node starts.

## The local control endpoint

A running node serves `bohio-via/1`, `bohio-links/1` and `bohio-pair/1` on `[control] endpoint`, a named pipe or a Unix socket. Whoever can connect may open, as this node, any stream any peer grants this node, list its links and arm a pairing PIN. The endpoint is not sealed, so it is guarded like the key:

- **Who may connect.** With no `socket_mode`, `socket_group` or `security_descriptor`, only this account may: the pipe or socket admits this user alone, and a client the system does not report as this user is closed unread. Setting any of the three replaces that with the operator's choice, and every account it admits holds all of the above.
- **Who is serving.** A client (`bohio remote --via`, `bohio links`, `bohio pair`) checks that the endpoint is served by its own account before it sends anything, and refuses another account's. A pipe name is visible to every user on Windows, so another account could bind it first while the node is down, and the node then runs without its control endpoint (it logs a warning); such an account would otherwise read every request (an exec's arguments, a file being written) and could answer `bohio pair` with a key of its own as the one that paired. With access settings in `[control]` the node may run as another account, and the client does not check: who may bind that name is then the boundary.
- On Unix the default socket is under `XDG_RUNTIME_DIR`, else `TMPDIR`; a directory others may write is refused by the node.

## Memory a peer can hold

Every buffer is bounded, but the bounds multiply. A proven peer with any grant can make a node hold, by not reading, up to `max_links_per_peer` links, each with `max_streams` streams, each with its receive window (`window`, 1 MiB; a host's `bohio-write/1` up to `bulk_window`; with `auto_window` up to `max_window`) plus two relay queues of `queue_bytes` (256 KiB). With the defaults that is 64 x 1.5 MiB, about 96 MiB a link, and about 1.5 GiB for one peer's 16 links; `max_connections` (128) bounds all peers together. A peer that is not trusted with that much memory needs a lower `max_links_per_peer` and `max_streams` on the node, or a node of its own. Unproven connections hold no more than one proof message each.

## Embedding

An application that runs a `bohio::node::Node` supplies its settings, identity, `Keys` and `Grants`; the node trusts them as given. [Embedding](embedding.md) shows how. What the API leaves to the application:

- **`Keys` decide who is a peer.** A `Keys` that accepts every key makes every key that proves itself a peer; `Grants` then decide what each may do, and `MemoryGrants` gives a key it has no entry for nothing. A question `Keys` cannot answer is `false`, and a `Grants` error refuses the stream.
- **`Keys::stranger` hears every proven key that is refused**, from anyone who can reach the node: bound what it keeps.
- **Bounds on connections are the listener's.** `Node::serve_listening` applies `max_connections` and `max_unproven_per_source`; `Node::serve_channel`, for a channel the application accepted itself, applies neither, so the application bounds how many it serves.
- **`Node::serve_local_channel` checks nobody.** It serves the local protocols to whoever is on the channel; serve it only on an endpoint the application's own account alone can reach (`local::Local` does that).
- **`NodeEvents` run on the link's thread.** An event sink that blocks holds up that link.
- **A node starts with an empty `PATH`**: programs are looked for where `Node::with_path` says.

## What the program list does

`exec.programs` limits **which program starts**, not **what it does**. A list holding `git` lets a peer start `git`, and `git -c alias.x=!command` runs any command; `make`, `find -exec`, `xargs`, `ssh`, `docker` and every interpreter run anything they are given. List only programs that are safe with every argument a peer can give them, and treat a list that names a build tool or an interpreter as no restriction.

With a non-empty list, each name is resolved on the host's own `PATH` to an absolute path and that path is started, never what the request's `PATH` or working directory would find, and an explicit shell script is refused (a shell runs anything). A request may set or remove only the environment variables `exec.env` names (`bohio peer approve --program NAME --env VAR`), and may not clear the environment. `PATH` is a variable like any other, so it is refused until it is named; once named, the listed program is still the one found on the host's own `PATH`, but whatever it starts runs what the peer's `PATH` finds: a variable is as strong as an argument, since `LD_PRELOAD` and `DYLD_INSERT_LIBRARIES` load a library the peer chose into the program, and `BASH_ENV`, `GIT_SSH_COMMAND` or `PYTHONPATH` make it run code the peer chose. Name only variables that are safe with any value. The working directory is still the peer's choice, and some programs read their configuration from it (`git` runs `core.fsmonitor` from a repository's own config), so a program that does is as strong as its configuration. An empty list means any program and any environment.

## Hashing costs the host disk and CPU

A hash reads every byte it covers, so a peer that holds `fs.read` can make the host spend its disk and processor without moving a byte over the link. `bohio-hash/1` is bound by `[hash] max_streams` (4; a stream past it is `busy`), by `[hash] rate` (bytes a second per stream, unlimited by default), by `[hash] algorithms` (what the host computes: the cryptographic ones cost more than `xxh3` or `crc32c`) and by `[filesystem] idle_timeout`. Hashing needs `fs.read` and a root, each item is resolved against the grant as it is when it is reached, and a missing file or a path outside the roots is that item's error and reads nothing. A peer can learn a file's digest, so one that may hash may confirm a guess at its content: that is within what `fs.read` already allows. Every write and read that names digests spends the same CPU, and is held to the same algorithm list. `md5` and `sha1` are offered for comparing with existing sums and are not collision resistant.

## What a forward gives a peer

`forward.connect` makes the host open connections for the peer, so the peer reaches what the host reaches, from the host's address: an internal service, a database, another machine's management port, and under a rule as wide as `*:*` a cloud metadata address or any address the host's network can route. A peer that holds it is as strong as the rules in its `[peer.<id>.forward] connect` list, which is why the permission alone allows nothing: a peer with no matching rule is refused before the host connects to anything, and a peer's grant of rules without the permission is refused the same way.

- **A rule is exact unless the operator wrote a pattern.** `HOST:PORT` names one target; `*.suffix`, `*`, an address range written as a CIDR network and a port range are the operator's choice, and each widens what a compromised peer reaches. Nothing is resolved when a rule is checked: an address or network rule matches only a target given as an address, so a name the peer supplies cannot be steered into a network by DNS, and a name rule trusts that name's DNS as any grant on a name does. To bind a grant to addresses, grant addresses.
- **A `unix:PATH` or `pipe:NAME` rule hands over what that socket or pipe is.** The container engine's socket is the engine's root, `/run/docker.sock` is a root shell, and a database socket is whatever its account may do. `*` and `?` in these rules do not cross a path separator, a path with a `..` part never matches, and a rule naming a directory's sockets (`unix:/run/user/*/bus`) grants every socket that directory ever holds. A named pipe is matched without case, as Windows compares them.
- **The bounds are settings.** `[forward] max_connections` (64, across peers) and `max_connections_per_peer` (16) bound how many connections a peer holds open, `connect_timeout` how long the host waits on a target, `chunk_size` and `stalled` how the pump moves bytes. A peer past a bound is told `busy`; none of them limits what a granted peer may reach.
- **A forward is decided like any stream.** The grant is read when the stream opens and again every `[link] recheck`: a peer that loses the permission or the rule has its running connections reset, and the target sees a reset, not a clean end. The host logs a `forwarded` event (the peer, the target's text, how it went) and never a byte of what the connection carried.
- **The client side of `-L` gives the grant to whoever can connect.** `bohio remote ... forward -L` binds `127.0.0.1` unless another address is named, and says `non-default: bind ADDRESS` when it is not loopback: a process or a machine that reaches that port has what the peer was granted, with no proof of its own. A local socket or pipe is for this user alone (`0o600`); on a shared machine another account's program can still reach a loopback port.
- **A `tcp/1` forward is the same capability.** `bohio-connect/1` and `tcp/1` are served under one grant, so a `coqui-link` peer does not widen what a peer may reach.

## Filesystem confinement

Every path resolves against a directory handle of a peer's `fs_roots`: `..` and an absolute path outside a root are `outside_root`, and so is a symbolic link that leaves a root, whether at the end of a path or in the middle. On Linux each lookup is one `openat2` with `RESOLVE_BENEATH` (kernel 5.6 and later), and elsewhere an `openat` walk that refuses to follow a link at each component, so a link swapped in while a call runs cannot lead out.

The root's owner is trusted: a hard link another local user makes to a file outside a root exposes that file, and a bind mount or junction an administrator places inside a root is part of the root.

## Container isolation

A container is a boundary only as strong as its runtime's configuration, and Bohío adds none to it.

- `bohio serve --stdio` inside a container, reached with `docker exec -i NAME bohio serve --stdio`, serves the container's own filesystem and processes. A peer's grant bounds what it asks for; the container bounds what that can reach. A peer with `exec` in a container can do what the container's user can do there.
- The image in `packaging/container/` runs as a non-root user with no extra capabilities. A container started with `--privileged`, extra capabilities (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`), the host's PID or network namespace, a mounted container-engine socket or a bind mount of the host's root hands that reach to every peer that may `exec` or `shell`, and Bohío cannot narrow it.
- Resource limits (memory, processes, CPU) are the runtime's. Bohío's `max_processes`, `max_sessions` and `max_transfers` bound how many things start, not how much they use.
- A shared kernel is shared: a peer that runs code in a container can attack the kernel. Where peers are not trusted with that, give each its own virtual machine.

## Privileged deployments

The risk grows with the account. A service run as `root`, `SYSTEM`, or any account in the `Administrators`, `docker` or `wheel` group, with a peer that holds `exec`, `shell` or `fs.write` outside a narrow root, gives that peer the machine.

- Prefer an unprivileged account. The systemd unit in `packaging/systemd/bohio.service` runs as `User=bohio` with `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true` and `PrivateTmp=true`, and writes only `StateDirectory=bohio`. `bohio service install` registers a Windows service as `NT AUTHORITY\LocalService`, which has no administrative rights (it does hold the right to impersonate, so a local user who could run code as it could go further).
- Whoever may change a configuration layer (the system file, the user's or any `--config` file) or the data directory decides who the host trusts and what each peer may do, and whoever may read the data directory holds the host's key; [Configuration layers](#configuration-layers) says how each layer is checked. On Windows every local user may add files and folders under `%ProgramData%`, and a folder made there inherits that, so `bohio serve` and the service refuse to start from a configuration file another account owns or every user may change, or from a data directory every user may change or read. Make `%ProgramData%\bohio` before installing the service and narrow its access list to the administrators, SYSTEM and the service's account (`icacls %ProgramData%\bohio /inheritance:r /grant:r *S-1-5-18:(OI)(CI)F *S-1-5-32-544:(OI)(CI)F *S-1-5-19:(OI)(CI)M`), or keep the default data directory in the service account's own profile.
- When a task needs more, widen it in the smallest way: a group that owns one directory, a command allowed through `sudo` for one account, a dedicated account for the deployment. Do not run the whole service as an administrator to let one peer do one thing.
- `fs_roots` set to `/` or a drive root, or a root that holds the account's own configuration (`bohio.cfg`, the `identity` key) lets a peer with `fs.write` change who else is trusted. Keep roots away from the data directory.
- A peer with `admin` is trusted to manage the host; no engine needs it today. Grant it to nobody.
- A client's `--fallback ENDPOINT` after a blocked UDP path is dialled as named: a `ws://` one is plain until the proof has run (the proof then seals what follows, but a path observer sees the first messages and the carrier's metadata), and one on another host sends the proof to that host, so name only a host whose key you trust. A refused certificate never falls back.
- `tls_valid_days` and `tls_cert` are the operator's: a certificate a browser will not accept pinned by its hash (valid over 14 days, or not ECDSA P-256) is logged once at start and works for every other client, which pins it by hash alone.
- A certificate is held to its dates even when pinned by hash. One made just now by a host whose clock is ahead of the client's is refused, with the hash and the start time named, until the client's clock reaches its start: `tls_backdate` (default an hour) starts the certificate a host makes earlier, and `bohio remote --clock-skew SPAN` accepts a start or end within SPAN of the client's clock (default none; it weakens only the dates). A certificate from files is made by whoever made it: start it earlier than now.
- On Windows the host refuses to start when another account may change its configuration file or data directory; `[service] check_access = false` lets it start from paths the operator owns and logs the finding, and then who may change those paths decides who may connect. A path another account owns is refused either way.
- `ws://` is served without TLS beyond loopback, because the proof seals every message after it. A peer that reads the network sees metadata (message sizes and timing) and the source address, not content.
- `wss://` and `webtransport://` add TLS for browsers (mixed content, `serverCertificateHashes`) and for proxies that pass only TLS. They are not the host's identity: a client trusts the host by the proof, and the TLS certificate only has to be accepted by the client's trust (`--ca FILE`, `--cert-hash HASH` or the system's roots). A certificate a client is told to trust by hash is trusted whatever its name and issuer, so pass a hash only over a channel you trust. The host reads `tls_cert` and `tls_key` when it starts and never logs them; keep the key file readable by the service's account alone. A WebTransport listener with no `tls_cert` makes its own certificate (ECDSA P-256, 13 days by default), prints its hash and makes a new one halfway through its validity: a client or browser pinned to the old hash must be given the new one, so a host that browsers pin for long should use a certificate from files that something else renews. A WebTransport client's `--fallback` is dialled as named, `ws://` and another host included (see the fallback note above).
- A listener that is reachable is attackable: bind to the narrowest address, use a firewall, and prefer `pipe://`, `serve --stdio` or a loopback address behind a tunnel when a peer is on the same machine. `[link] max_connections` and `proof_timeout` bound what an unproven connection may cost; `max_unproven_per_source` keeps one address (or one IPv6 /64) from holding every slot while proving nothing, and `max_links_per_peer` keeps one proven peer from holding them with links. Behind a reverse proxy every peer has the proxy's address, so the per-source bound is shared by all of them there; many sources at once can still fill `max_connections`.

## Known limits

These are recorded and not fixed. Each is a platform limit, a window that needs a local attacker, or a bound on what cleanup can promise.

- **Ending a process tree is cleanup, not containment.** The host ends what a program leaves behind by accident; a peer that may run any program and means to leave one running can. On Unix a double fork with `setsid` leaves both the process group and the parent chain the host walks; on Windows a program can ask the WMI or Task Scheduler services to start one outside its job object. Such a process runs as the service's account until it exits, and while it holds the output pipe of the program that started it, one host thread waits on that pipe. Only a peer trusted with `exec` without a program list (or with a listed program that starts others on request) can do this; `KillMode=control-group` ends them with the unit.
- **Windows directory calls are path-based.** On Windows `list`, `readlink`, `mkdir`, `remove`, `rename`, `symlink` and `set_attributes` resolve the parent through its current path and join the name, because the library that confines file access does not offer handle-relative calls there. A local user who can rename a directory inside a root while one of these calls runs can redirect it outside the root, so the call then acts as the service's account on what lies there. A peer cannot do this alone: a link it makes has a relative target that stays inside by its words, and Windows takes the `..` of a link's target by its words. `stat`, hashes, reads and the opens of writes are handle-relative and not affected. The root's own path is opened by path on every platform. The fix needs `NtCreateFile` and `SetFileInformationByHandle` relative to the parent's handle; until then, do not give a root to a peer on a Windows machine where an untrusted local user can write to the root's directories.
- **On Unix a chain of links a peer makes can lead out of its root for other programs.** Each link's target must stay inside the root by its words, but `sub/d` naming `..` and `esc` naming `sub/d/..` together name the root's parent, because the kernel resolves `..` after following `sub/d`. The host's own calls refuse such a path; a program that follows links in a root without a directory handle (a backup job, a web server serving it, a process a peer starts) does not. Do not point such a program at a root a peer may write.
- **A Windows process starts a moment before it joins its job object.** A process the program starts in that instant is outside the tree and survives an ended session, a `kill` frame or a deadline. A shell's terminal starts its child itself, so the same moment applies to a shell session. A program that spawns children in its first milliseconds can leave one behind.
- **A killed `serve` on Unix leaves the exec trees it started.** The host ends a tree when its stream closes, on a deadline and on a `kill` frame. A host that dies without running that code (`SIGKILL`, the operating system's out-of-memory killer, power loss) leaves the processes it started, in their own process groups, running. A Windows host's job object ends them when the process dies. The systemd unit uses `KillMode=control-group`, so stopping or restarting the unit ends every process in its control group; a service manager without that does not.
- **A serial line has one peer at a time, and a reconnect can lose a message.** The host opens the port, serves one link and opens it again about 250 ms later, discarding what arrived before. A client whose first message arrives before the host has reopened the port, such as a second `remote` right behind the first, is dropped and must try again. Each failed attempt costs the proof timeout.
- **`peer approve` and `peer revoke` edit a layer in place** (only the peer's table changes; the file's comments and layout stay) and replace the file atomically; two such commands at the same instant can lose one change. A layer the account cannot write is skipped by `approve`, and `revoke` names it: the key stays accepted there.
- **Only `[peer.*]` is read live.** Every other section is read when the host starts. A layer that cannot be read or parsed refuses every peer (logged once per distinct error) until it is fixed.
- **A revoked peer's link ends at its key check** (`[link] key_recheck`, twice `recheck` unset) at the latest; its streams end at the first recheck or at that check, whichever comes first, and either way the peer is told they were revoked. Between a revoke and that point a running stream goes on, and the node's own streams to that peer (`bohio remote --via`) may still be opened.
- **Two nodes that dial each other at the same moment hold two links.** Both serve, under the same grants, and each counts against `max_links_per_peer`; a dialer waits while one is up, so the pair settles at one once either ends.
- **The control endpoint's same-user check has not been tried against a second account on Windows.** The default access list admits this user alone, so the system refuses another account before the check is reached; a process of this account at a lower integrity level is refused by the label an elevated node adds. Any program this account runs may use the endpoint, as it may read the key.
- **A peer's text reaches the terminal as it is.** `bohio links` prints the protocol names a peer's `link/1` document offers and `bohio remote info` what a host reports, without removing terminal control sequences, so a peer can change how the operator's terminal shows them.
- **The data directory is not checked on Unix.** A data directory another account may write lets it replace the node's `identity`; keep it under the account's own home or `StateDirectory`.
- **A message or a key is never logged, but a process list is public.** `exec` argument vectors are not logged by the host; a program started on the host appears in that machine's process list with its arguments. `bohio join --pin` puts the PIN on a command line; without `--pin` it is read from standard input.
- **A service has no console.** A Windows service writes its diagnostics to standard error, which nothing reads; run the command in a terminal with `BOHIO_LOG` to see them. Under systemd they go to the journal.
- **A Windows named pipe has no half-close.** A forward to a pipe ends both directions when the client ends its own, so a pipe server that answers only after the end of its input gets none; one that answers each message works. A Unix socket half-closes.
- **A forward's reset reaches only what the pump can end.** A revoked forward is cut at the next `[link] recheck` (a connection already closed by the target has nothing left to cut), and a connection to a Unix socket or a pipe is ended by closing it, not by a reset, which those do not have.
- **A loopback connect to a closed port in the ephemeral range can connect a socket to itself.** `bohio join` and the client refuse such a connection.

## Reporting

A security problem is reported privately to the maintainers at `contact@boriken.dev`, not in a public issue.
